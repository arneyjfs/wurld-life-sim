# Text-to-Speech (TTS) — infrastructure spec

> Single source of truth for spoken audio across the app. TTS is
> consumed by four surfaces — practice mode (listen-* questions + an
> opt-in speak button on other question types), the chat message
> "Read aloud" action, the Explain modal language cards, and life-sim
> dialogue bubbles — plus a Settings voice-preference preview. All of
> them route through ONE Cloud Function (`synthesizeSpeech`) and ONE
> client player (`src/lib/tts.ts`), so the engine is swapped in one
> place and every surface inherits it.
>
> Invariants are prefixed `TTS-<SECTION>-<N>`. Grep an id to find the
> tests that assert it.

Coordinates with [practice-mode.md](./practice-mode.md) (owns the
listen-question UIs + the prefetch loop), [wurld-tutor.md](./wurld-tutor.md)
(the voice preference also sets the tutor's gender), and
[life-sim.md](./life-sim.md) (dialogue-bubble TTS). See "Cross-spec
touchpoints" at the end.

## Mental model

```
  surface (practice / read-aloud / explain / life / settings preview)
        │  text + languageCode + {speechSpeed, gender / voiceName}
        ▼
  src/lib/tts.ts   playTTS() | prefetchTTS()        ← cache, playback singleton, progress
        │  callHttp('synthesizeSpeech', …)
        ▼
  functions: synthesizeSpeech   ← Gemini TTS via Cloud Text-to-Speech
        │   flash-primary for every call; style prompt by `speechSpeed`; voice by gender / name
        ▼
  base64 audio (container)  →  blob URL  →  one <audio> element
```

The engine is **Gemini TTS on the Cloud Text-to-Speech surface** —
the model is selected per call via `VoiceSelectionParams.model_name`;
the same `synthesize` request shape serves both models, so fallback is
a one-field change.

## TTS-ENGINE — model, fallback, voice, format

| ID | Rule |
|---|---|
| **TTS-ENGINE-1** | All synthesis goes through the single `synthesizeSpeech` Cloud Function. No surface calls a TTS API directly; no second synthesis path exists. The function speaks Gemini TTS via the Cloud Text-to-Speech `synthesize` endpoint (`model_name` on the voice selects the model). |
| **TTS-ENGINE-2** | **Every surface is flash-primary.** On-demand (`preload` false: read-aloud, explain card, life dialogue, the vocab card, settings preview) AND pre-warmed (`preload` true: practice) both try `gemini-2.5-flash-tts` first, and fall back to `gemini-2.5-flash-lite-preview-tts` only when flash fails (TTS-ENGINE-3). The constants are `TTS_MODELS.flash` / `TTS_MODELS.flashLite`; `ttsModelOrder` returns `[flash, flashLite]`. *(`preload` RETIRED 2026-09-29 — audit DEAD-14: the client no longer sends it, the server no longer reads it, and it is no longer part of the cache key.)* *(Owner, 2026-09-25: move everything still on Flash Lite to Flash. Until then on-demand calls were lite-primary for latency — see Design decisions.)* |
| **TTS-ENGINE-3** | **Fallback + retry.** The documented Gemini-TTS failure mode is "returns text tokens instead of audio → 500". On error (5xx, model-unavailable, or a non-audio response): retry once on the SAME model, then swap `model_name` to the other model with an identical payload and retry once. Fallback is same-surface only (request shape + voices + languages are shared). Total budget ≤ the function timeout (60s). If both models fail, return a structured error; the client surfaces a non-blocking failure state (TTS-BUTTON-4), never a crash. |
| **TTS-ENGINE-4** | **Voice = gender → one of two voices.** `voiceGender: 'MALE' \| 'FEMALE'` maps to a fixed clear Gemini voice (MALE → `Iapetus`, FEMALE → `Erinome`). Voices are shared across both models, so the choice survives a fallback. The mapping is a single server-side table; no per-language voice list. |
| **TTS-ENGINE-5** | **Output is a directly-playable container**, requested as MP3 from Cloud TTS, so the client wraps it in a blob URL and plays it through a plain `<audio>` element with no PCM/WAV handling. If a model path can only emit `LINEAR16`, the function wraps it in a 44-byte WAV header (mono, 24 kHz, 16-bit) before returning — the client contract is always "a playable audio container in base64". |
| **TTS-ENGINE-6** | The request carries `languageCode` (BCP-47, from `getTTSCode`). It is passed as `VoiceSelectionParams.language_code`. A request that arrives with no/empty `languageCode` is rejected before the LLM call (TTS-LANG-1 prevents this client-side). |
| **TTS-ENGINE-7** | Per-call usage is recorded to the usage-stats counters, partitioned by the model actually used, fire-and-forget. **Both sides are recorded: text-input tokens AND audio-output tokens.** Gemini-TTS bills text input plus audio output at **25 audio tokens per second of speech** ($0.50/1M in, $10.00/1M audio out, no free allowance), and audio output is essentially the whole bill. The Cloud TTS `synthesize` response carries no usage metadata, so the audio-token count is DERIVED from the returned audio: `mp3DurationSeconds` parses the first CBR frame header, and `ttsAudioTokens` converts duration to tokens, falling back to a words-per-second estimate over the spoken text when the audio cannot be parsed. It never returns 0. *(Until 2026-08-11 this path recorded a hard-coded `0` output, reporting TTS at roughly 0.3% of its real cost — a ~270x under-report, and the only category whose dashboard figure was not merely imprecise but meaningless. Asserted by `ttsSynth.test.ts`.)* |

## TTS-STYLE — difficulty-aware pacing

| ID | Rule |
|---|---|
| **TTS-SPEED-1** | **Speech pace is a dedicated user pref, INDEPENDENT of difficulty, applied APP-WIDE.** `users/{uid}.speechSpeed` ∈ 1–4 governs delivery on EVERY surface — chat read-aloud, practice, explain, life-sim. The scale: **1 "Clearer" / 2 "Clear"** → progressively clearer, more distinct articulation (clarity, NOT slowness — the `speechSpeedPrompt` in functions/src/ttsSynth.ts explicitly forbids dragging words / long pauses / stilted delivery); **3 "Natural" = the DEFAULT**, returns `undefined` (no prompt → the model's natural native pace, so a user who never touches the slider pays no extra latency); **4 "Fluent"** → a fast, very casual native delivery with contractions/reductions, for advanced ears. `speechSpeed` is threaded automatically: `TTSButton` reads `profile.speechSpeed` (like `voicePreference`) so no surface has to pass it — unless an explicit `speechSpeed` prop overrides it (the Settings preview); `usePracticeTtsPrefetch` reads the same value so prewarm keys match play-time keys. Server + client default to 3 when unset. Difficulty no longer influences pace anywhere. |
| **TTS-SPEED-1.1** | **The native language always plays at natural pace** (owner, 2026-10-20). `speechSpeed` is a learning aid for the language being learnt, so `TTSButton` drops it when the clip's language shares its primary subtag with the user's `nativeLanguage` (an en-GB speaker hearing en-US text too), unless an explicit `speechSpeed` prop is passed (the Settings preview). |
| **TTS-SPEED-1.2** | **Speech speed is per practice language** (owner, 2026-10-20). `users/{uid}.speechSpeeds[practiceStatsKey(language)]` ∈ 1–4, read through `speechSpeedFor(user, language)` (`src/lib/level.ts`): the language's own entry, else the old global `speechSpeed`, else undefined (natural, 3). `TTSButton` resolves it from its `language` prop; `usePracticeTtsPrefetch` and Wurlds' prefetch resolve it from the same language, so pre-warm keys still match play keys (TTS-CACHE-1). Native language still plays at natural pace first (TTS-SPEED-1.1). Settings edits it per language tab (settings-screen.md SETTINGS-LANG-3). As with level (XP-LANG-3), no migration: `speechSpeed` is every language's starting value. |
| **TTS-STYLE-3** | There is no numeric `audioConfig.speakingRate` parameter — the Gemini TTS voices are prompt-steered, so pace is governed solely by the `speechSpeedPrompt` (TTS-SPEED-1) passed in the Cloud TTS `prompt` field, separate from the spoken `text`. Bracketed audio tags, if any, stay in English even for non-English text. |
| **TTS-STYLE-4** | *(Amended 2026-10-21, SETTINGS-GROUP-1.)* In Settings, speech speed lives in the **Learning** group (`LearningSection`): the Speech speed slider sits under the Quiz level slider, both driven by ONE language tab row (SETTINGS-LANG-2). Voice lives at the bottom of **App preferences** (`VoiceQuizSection`, SETTINGS-LANG-4), under a sub-header + description. Level's onboarding card (`DifficultySection` / `DifficultyControl`, `requiredSeed`) is unchanged. The speech-speed control is a 1–4 clarity slider (4 = the fastest; draft-during-drag, commit-on-release, wheel-guarded) writing `speechSpeeds[key]` for the selected language (TTS-SPEED-1.2). The voice control renders the Female/Male chips (each with its preview) on ONE row, stacking vertically only on very small screens (`min-[360px]:flex-row`); each preview's `TTSButton` is passed `voiceGender={that chip's gender}` AND `speechSpeed={the practice language's saved speed}`, so **the preview reflects BOTH selections**. (Until the 2026-10-21 fourth pass Voice sat beside the slider and previewed its draft speed.) `TTSButton`'s `speechSpeed` prop overrides the profile value (falling back to it), mirroring `voiceGender`. |
| **TTS-STYLE-4.1** | *(The speech-speed instance of settings-screen.md `SETTINGS-SLIDER-1`, implemented by the shared `useSliderCommit` hook.)* **"Commit-on-release" means EVERY way a slider interaction ends — the setting is never lost to a gesture the browser ended differently.** The speed is written when the interaction ends by `pointerup`, by **`pointercancel`** (a touch drag the browser takes over or ends — iOS WebKit does this routinely), by the native range **`change`** event (fires on commit in every engine, including when no pointer events fire at all), by `keyup`, OR by the screen unmounting with an uncommitted draft (navigating away mid-interaction). Every path writes the LATEST draft (read from a ref, not from the event target at that instant), and a value already written or already equal to the persisted one is not re-written, so the overlapping paths cost one write. *(Bug 2026-09-25: the owner changed the speed and, on navigating away and back, found the old value. Only `pointerup`/`keyup` committed; `pointercancel` cleared the drag flag and dropped the draft, and the stuck drag flag then also blocked the draft from re-syncing to the persisted value.)* |

## TTS-VOICE — the voice belongs to the SPEAKER

| id | invariant |
|---|---|
| **TTS-VOICE-1** | **The full 30-voice Gemini prebuilt table lives in `src/lib/ttsVoices.ts`, transcribed — never inferred.** `TTS-ENGINE-4` shipped with exactly TWO voices (`Iapetus` male, `Erinome` female), so every character in every wurld spoke in one of them, and WHICH one came from the *player's* `voicePreference` rather than from who was talking. Owner, 2026-08-06: *"Gender of tts should be set to match the gender of the speaker, maybe shuffling available voices if possible, not obeying global default gender."* **Getting a voice's gender wrong is the exact defect being fixed**, so the table is copied from Google's own pages — genders from `cloud.google.com/text-to-speech/docs/gemini-tts#voice_options`, characteristics from `ai.google.dev/gemini-api/docs/speech-generation` — and the two agree with the code that was already here: both give `Iapetus` male / `Erinome` female, both **Clear**, which is what `ttsSynth.ts` had called them (*"a fixed clear Gemini voice"*) before the table existed. Three independent sources agreeing on the two voices already in production is the reason to trust the other 28. **Row order is load-bearing** — the per-speaker pick hashes into the list, so re-ordering re-casts every character in every wurld. Append, never insert. 16 male / 14 female; each of the five registers (`warm · firm · bright · calm · rough`) is reachable for both genders, asserted by test. |
| **TTS-VOICE-2** | **One speaker, one voice — hashed per WURLD, and speed is not part of it.** `voiceForSpeaker({ worldId, speakerId, gender, register })` picks by FNV-1a over `worldId:speakerId`. **IN the hash:** the wurld. Owner: *"hashed for each wurld but not between wurlds as register changes"* — the same character id in two wurlds is two different people and may sound different, while inside one wurld a character keeps their voice for its whole run, with nothing persisted and no extra field to migrate. **OUT of the hash: `speechSpeed` and difficulty.** Owner: *"difficulty/speed should not be part of hash and separate in the prompt so if the user changes mid session it applies."* Speed is a global setting delivered through the Cloud TTS `prompt` field (`TTS-SPEED-1`/`TTS-STYLE-3`), wholly beside voice selection — so dragging the slider re-synthesises the same character at a new pace and never re-casts them. `speechSpeed` IS in the cache key (`TTS-CACHE-1`) because it changes the audio; that is a different question from which voice to use, and `cacheKey` is where the two visibly part. **No gender ⇒ empty string**, and the caller falls back to the player's preference: guessing a gender from an id is what this invariant exists to stop. An unrecognised `register` widens to the whole gender pool rather than failing. |
| **TTS-VOICE-3** | **The server validates the client's choice against its own allowlist.** `synthesizeSpeech` accepts an optional `voiceName`; `ttsVoiceFor(voiceName, voiceGender)` honours it only if it is in `GEMINI_VOICE_NAMES`, else falls back to the gendered default. Silently — the caller may be a stale client, and a wrong-sounding voice beats a failed synthesis on the one call the player is waiting for. The list is DUPLICATED in `functions/src/ttsSynth.ts` because functions cannot import from the app build; a unit test in `src/lib/ttsVoices.test.ts` reads the server file and asserts the two name the same 30 voices, so the copies cannot drift silently (same technique as `harnessShape.test.ts`). |
| **TTS-VOICE-5** | **The life sim CASTS its characters: `ZCastMember.gender` + `voiceRegister`, authored by `sagaOpen`.** Nothing in the life sim recorded a character's gender before 2026-08-06 — the cast carried name, `known`, `voice` (*how* they talk), standing and ties, but nothing about who the player HEARS. Both fields are on the character sheet rather than on the question, because a voice is an attribute of a person: re-deciding it per question would let the same NPC change voice between turns, which is the thing `TTS-VOICE-2`'s per-wurld hash exists to prevent. `gender` is **REQUIRED** in `sagaOpen`'s response schema AND named in its output CONTRACT — `LIFE-ARCH-8`'s `playerFacingTeaser`, `LIFE-INTENT-2`'s `leaning` and `LIFE-EX-VOCAB-4`'s `lineVocab` all shipped as fields that were declared, described in prose, and absent from the JSON skeleton, so *optional + absent = silently never emitted* is a mistake this codebase has now made three times. `other` is a genuine answer for a character no binary voice suits, and falls back with everything else rather than being coerced. **Two seams carry them or the field dies quietly:** `normaliseMember` rebuilds a member field-by-field (deliberately — a regular must LOSE `wants`), and `applyCastChanges` runs on EVERY `sceneClose`, so a gender not threaded through both would survive one scene and vanish for the rest of the wurld. Gender + register join `name` and `known` in the never-re-emittable bucket: a close may move `voice`, `standing`, `wants`; it may not re-cast the character mid-story. |
| **TTS-VOICE-6** | **`LifeScreen` is the only place that can answer "who is speaking", so it is where the voice is resolved.** The comprehension prompt names its speaker (`npcId`, pinned from the direction by `LIFE-EX-DIR-2`); the world's cast holds their gender and register; `voiceForSpeaker` turns the three into a voice, threaded down as `speakerVoiceName` to `LifeScreenBottom` → `ListenComprehensionCard` → `TTSButton`. **Every fallback lands on the OLD behaviour** — a prompt that is not a comprehension, one with no `npcId`, a character the cast has no gender for (i.e. every world created before this shipped) all resolve to `''`, which `TTSButton` reads as "no override" and answers with the player's `voicePreference` (`TTS-PREF-1`). So a legacy world is exactly as it was, and no migration is required for one to keep working. `voiceName` is plumbed through `TTSButton` generally but passed by the life sim ALONE; every other surface (chat read-aloud, practice, explain, the Settings preview) is the player's own voice by definition and leaves it undefined. |
| **TTS-VOICE-4** | **The live voice list is NOT reachable from a build environment, and that is why the table is hand-held.** `texttospeech.googleapis.com/v1/voices` refuses API-key auth outright — *"API keys are not supported by this API. Expected OAuth2 access token or other authentication credentials that assert a principal"* — on both `v1` and `v1beta1`. Note the consequence for `listStandardVoices`, which calls that endpoint with `?key=`: it cannot be working in production either. Left alone here (different surface, different change), recorded so the next person does not re-derive it. |

| **TTS-VOICE-7** | **A graded question's audio starts loading a WHOLE GEMINI ROUND-TRIP before the question exists.** Owner, 2026-08-06: *"Tts should load at the earliest possible moment and play automatically as soon as it lands."* Autoplay already fired on card mount, but the card mounts only after `runGradedQuestionGenerate` returns — seconds of a Gemini call during which the line to be spoken was, in fact, already known: a comprehension `gradedPlan` carries `npcUtterance`, authored by the STEP call one round-trip earlier (`LIFE-EX-PLAN-5`). So the synthesis now runs INSIDE the generation instead of after it. Fire-and-forget: it either wins the race (the card mounts to a warm cache and speaks instantly) or loses harmlessly (autoplay synthesises on demand, exactly as before). **Fill-blank stands down** — its audio is the COMPLETED sentence, which does not exist until the chips do (`LIFE-EX-9`). **The prefetch is only worth anything if it lands on the key playback will ask for**, so `speechSpeed` is threaded into the engine from the profile and passed THROUGH rather than defaulted (inventing a 3 would mis-key every user who has never touched the slider), and the voice comes from the same `voiceForSpeaker` call the card will make. A prefetch in the wrong voice or at the wrong speed is not a slower prefetch — it is a paid clip nobody hears. |
| **TTS-VOICE-8** | **The line that was warmed is the line that gets played: `pinPlannedUtterance`.** Warming from the plan is only sound if the generator's `npcUtterance` IS the plan's. The SI says *"copy from plan, do not paraphrase"* — and nothing checked it, so the pre-warm would have been correct by luck. **MEASURED over 75 archived comprehension questions: 100% verbatim.** Reliable is not guaranteed, so the value is NORMALISED rather than rejected — the right answer is known in code, a retry could only reproduce it, and this is the same call `applyGradedDirection` makes for `speakerName`/`npcId` (`LIFE-EX-DIR-2`). Divergence is logged, so if the model ever starts drifting the rate is visible instead of silently costing one wasted synthesis per question. |
| **TTS-VOICE-9** | **The BUBBLE's speak button uses the character's voice too — one voice per person, on every surface that speaks them.** Reported 2026-08-07: *"All the work you did attributing a tts voice to a character, please make sure it is attached to the character also when the button just above the message bubble is hit."* `TTS-VOICE-6` resolved the cast voice in `LifeScreen` and threaded it as `speakerVoiceName` to exactly ONE consumer — `LifeScreenBottom` → `ListenComprehensionCard`, i.e. the listening EXERCISE. The per-bubble button (`TTS-SURFACE-4`, beside the NPC's name above their bubble) is a different component on a different path and was never given it, so the same character read her line in her own voice inside the exercise and in the PLAYER's voice when her bubble was tapped — on the surface the player touches most. **The gap is the shape, not the value:** the voice was computed correctly and delivered to part of the app, which is why nothing failed and no test noticed — the same class as `LIFE-GRID-6`'s backstop with no callers. So the resolution moves out of the screen into `castVoiceMap(world)` (`cast.ts`), returning npcId → voice for the WHOLE cast: the dialogue area needs it for any bubble on screen, two NPCs can be visible at once, and a pure function is testable without mounting a screen that no test renders. Threaded exactly like `npcAvatarUrls`, for the same reason — `LifeScreen` is the only place holding the cast. **Members with no usable gender are OMITTED rather than mapped to `''`**: both reach `TTSButton` as "no override" (⇒ the player's `voicePreference`, `TTS-PREF-1`), and omission keeps the map honest about who has actually been cast — which is nobody in every world created before `TTS-VOICE-5`. `other` falls back with them rather than being coerced into a binary pool. **The USER bubble is the deliberate exception and is asserted as such**: it is the player's own line and stays on their own voice; sweeping it in while fixing this would put the player's words in somebody else's mouth. |
| **TTS-VOICE-10** | **The cast's voice assignment is LOGGED, because three causes were indistinguishable from the outside.** Reported 2026-08-08: *"Madame leclaire speaks with a male voice, but I don't have the necessary logs to see if the model assigned the wrong gender, or if one of the voices is assigned female but sounds male."* Exactly the right question, and nothing on screen could answer it. Three candidates: (a) `sagaOpen` wrote `gender: 'male'` for her; (b) her cast row carries NO gender, so `castVoiceMap` omits her and `TTSButton` falls back to the PLAYER's `voicePreference` — which, if that is male, makes EVERY uncast NPC male and is the most likely explanation for a whole-cast symptom; (c) `GEMINI_VOICES` mislabels a name. `castVoiceMap` now emits one `lifeDebug('SAGA', 'cast voices')` per world carrying, for every member, the id, the gender as stored (`MISSING` when absent), the register, and the resolved voice — with uncast members listed explicitly as `(player default)` rather than silently skipped. (a) and (b) are then read straight off the overlay and (c) narrows to a specific voice name to listen to. The 30-row gender table was re-checked against Google's published list and matches; that does not clear (c) — a correctly-labelled voice can still SOUND wrong to a listener — but it does mean no row is provably mislabelled. |
| **TTS-PREWARM-1** | **Practice warms EVERY listen-* question the moment it is generated, not a rolling window.** Owner, 2026-08-07: *"make sure that the tts for actual practice questions is loading at earliest point, as soon as the sentence is generated as designed earlier, and it starts playing as soon as the TTS lands."* The life sim already worked that way — `TTS-VOICE-7`'s `prefetchPlannedUtterance` fires BEFORE `runGradedQuestionGenerate`, so synthesis overlaps generation — but `usePracticeTtsPrefetch` warmed `idx .. idx+3`, so a question at position 7 had no audio requested until the player reached position 5 and the first tap waited on a synthesis that could have been running for a minute. **The window was a cost control and it is the wrong one here:** a `listen-*` question is SPEECH-BASED, the audio IS the question, so it WILL be played — which is the same distinction `TTS-SURFACE-1` already draws when it forbids warming the OPTIONAL speak buttons on visual questions (those stay on-demand, asserted). The only clip this wastes is one in an abandoned session; what it buys is that no listen question is ever the first to ask for its own audio. Warming starts at the CURRENT index so a resumed session does not re-request its own history. |
| **TTS-CACHE-4** | **A synthesis already IN FLIGHT is neither re-issued nor raced.** Two halves of one defect, both invisible while the practice prewarm was three questions wide. (a) `prefetchTTS` skipped only what was already CACHED, so N calls for the same clip inside the synthesis window meant N paid requests — the rolling window re-prefetched its three on every advance, and `TTS-PREWARM-1` re-runs the effect on every streamed arrival, which would multiply it. (b) `playTTS` checked the cache and, finding it empty, started its OWN synthesis beside the prewarm already running — and the autoplay path hits that window nearly every time, because the question is prewarmed when it generates and its card mounts a moment later. So the in-flight map holds the PROMISE, `prefetchTTS` skips a key that is pending, and `playTTS` AWAITS a pending one before falling back to synthesising. That is what makes *"starts playing as soon as the TTS lands"* literally true: the autoplay resolves on the prewarm's own clip rather than on a second copy of it. The slot is cleared in `finally` — on failure as much as success — because an in-flight entry that only cleared on success would turn one transient error into a clip that can never be requested again for the rest of the session. |

## TTS-LANG — language support gating

| ID | Rule |
|---|---|
| **TTS-LANG-1** | A language supports speech **iff** `getSpeechLanguageCode(language)` returns a code — i.e. `ttsCode` is present AND `ttsUnsupported` is not set. (`ttsCode` stays the canonical BCP-47 code, also used for display localisation, so it is NOT removed from speech-unsupported languages; the dedicated `ttsUnsupported` flag gates speech.) Every TTS surface gates on `getSpeechLanguageCode` before showing a speak affordance or issuing a request. |
| **TTS-LANG-2** | Every `ttsCode` in `SUPPORTED_LANGUAGES` that is NOT marked `ttsUnsupported` MUST be a member of the canonical Gemini TTS locale set, with exact casing. A frozen-set unit test asserts this and fails on drift. (Fixes at adoption: `ar-SA`→`ar-001`, `cmn-TW`→`cmn-tw`, `jv-ID`→`jv-JV`; `ga-IE`/`gd-GB` keep their BCP-47 `ttsCode` for display but gain `ttsUnsupported: true`.) |
| **TTS-LANG-3** | The language picker shows a "speech not supported" affordance (muted-speaker label) on any language whose `ttsCode` is absent. Selecting it is allowed (text features still work); only audio is gated off. |
| **TTS-LANG-4** | When the user's **practice** language has no `ttsCode`, practice generation is run with `noAudio = true` so listen-* question types are never planned (`allowedPracticeTypes(difficulty, noAudio)`). A no-TTS practice session is fully playable with the non-audio question types. |

## TTS-CACHE — caching + playback singleton

| ID | Rule |
|---|---|
| **TTS-CACHE-1** | Synthesised audio is cached client-side keyed by `(languageCode, voice, speechSpeed, text)` where `voice` is the explicit `voiceName`, else `voiceGender`, else `auto`. `speechSpeed` (defaulting to 3) is folded in on EVERY surface because it varies the audio everywhere (TTS-SPEED-1). *(The former `mode ∈ {natural, learner}` term — keyed off `preload` — was RETIRED 2026-09-29, audit DEAD-14: the server ignores which surface asked, so the split only duplicated synthesis; a clip pre-warmed by practice now serves an on-demand tap of the same text at the same speed and voice.)* `prefetchTTS` warms the cache; `playTTS` reads it. |
| **TTS-CACHE-2** | Exactly one audio element plays at a time (global singleton). Starting playback stops any current playback; tapping the active surface's button stops it (tap-to-stop). Screen unmount calls `stopPlayback()`. (Inherits the practice-mode singleton contract; now app-wide.) |
| **TTS-CACHE-3** | Practice pre-warms the **next questions ahead** (≥1, currently a 3-question look-ahead) AND warms the first question during `LessonIntro`, using the user's `speechSpeed` + resolved voice so the warmed clip matches what playback will request (same cache key). **Scope: only SPEECH-BASED (listen-*) questions are pre-warmed** — `ttsTextFor` returns `null` for visual question types (multiple-choice, find-the-mistake, native-to-practice, vocab-matching) so the look-ahead skips them (TTS-SURFACE-1). Their optional speak buttons synthesize on demand. |
| **TTS-CACHE-4** | The playback subscription emits BOTH a state (`idle\|loading\|playing\|error`) AND a progress fraction (0–1, from the audio element's `currentTime/duration`) so a button can render a progress ring. Progress resets to 0 on stop/idle. |

## TTS-BUTTON — shared 3-state speak button

| ID | Rule |
|---|---|
| **TTS-BUTTON-1** | All inline speak affordances render through ONE shared component (`<TTSButton>`). It is small and icon-only by default. Surfaces: practice question prompts, Explain modal language cards, life-sim dialogue bubbles, the Settings voice preview, the vocab word card (TTS-SURFACE-5), AND the chat per-message inline control (TTS-SURFACE-2a). The chat "Read aloud" action remains a menu ROW that *starts* playback (TTS-SURFACE-2); while it plays, the inline control beside that bubble (also a `<TTSButton>`) is the live affordance. |
| **TTS-BUTTON-2** | Visual states: **idle** = speaker icon; **loading** = an indeterminate spinner ring around the button's outside edge; **playing** = a determinate progress ring (driven by TTS-CACHE-4 progress) around a **stop** (square) glyph, tap = stop. The button derives its state from the playback subscription keyed to its `playbackKey`. |
| **TTS-BUTTON-3** | A button whose language has no `ttsCode` (TTS-LANG-1) is not rendered at all (not a disabled button) — absence of audio is silent, not an error affordance. |
| **TTS-BUTTON-4** | On synthesis failure the button shows a brief error state then returns to idle; it never blocks the surface or throws. |
| **TTS-BUTTON-5** | **The `bare` variant** (added 2026-10-24 for the vocab card, MSG-VOCAB-9.5). Same component, same playback state and tap behaviour, drawn as a bare icon with no circle, fill or ring, so it can sit inside a line of text: **idle** = speaker, **loading** = the spoked `Loader` glyph spinning in place of the speaker (the same spinner as the card's save button; owner 2026-10-24 preferred it to `Loader2`'s arc), **playing** = speaker with sound waves, tap = stop. It takes the surrounding text colour. TTS-BUTTON-2's rings belong to the default circular variant only. |

## TTS-PREF — voice preference setting

| ID | Rule |
|---|---|
| **TTS-PREF-1** | The user profile carries `voicePreference: 'male' \| 'female'`. It is the single source for (a) the TTS `voiceGender` on every call app-wide, and (b) the tutor's gender (TTS-PREF-4). Stored via the same `writeUserSetting` path Settings uses for difficulty. |
| **TTS-PREF-2** | The control lives in Settings **below the difficulty control**, with a one-line hint: it sets the speaking voice across the app AND the **persona** of the Wurld tutor (no longer phrased as "a man or a woman"). |
| **TTS-PREF-3** | Each option (Male / Female) carries a canned-example play button that synthesises a short fixed phrase in the user's practice language, in that voice, at the DRAFT `speechSpeed` (TTS-SPEED-1) so the user previews the pace they are choosing. Each option chip also shows the learner's current **level band** (e.g. "Female · Level 1–2"), derived from the profile difficulty, so the preview's pacing is self-explanatory. A sub-hint states difficulty pacing applies in practice sessions; elsewhere speech is natural pace. |
| **TTS-PREF-4** | The tutor's persona gender + the `senderPronouns` pinned on tutor messages (used for translation gender agreement) derive from `voicePreference` (`male`→`he`, `female`→`she`). This SUPERSEDES any previously hard-coded tutor gender. Changing the preference changes the tutor on the next reply; already-sent tutor messages are not rewritten. |

## TTS-SURFACE — per-surface wiring

| ID | Rule |
|---|---|
| **TTS-SURFACE-1** | **Practice.** Listen-* questions (`listen-and-pick/write/fill`) are SPEECH-BASED — the audio IS the question — and auto-play on mount (existing `PRACTICE-Q-LP/LW/LF`). Other question types (multiple-choice, find-the-mistake) are visual and get an OPTIONAL, non-autoplay `<TTSButton>` on their practice-text. Practice synthesis is the same flash-primary call at the user's `speechSpeed` as every other surface (TTS-ENGINE-2, TTS-SPEED-1). **Only speech-based (listen-*) questions are pre-warmed** — the look-ahead (`ttsTextFor` → non-null only for listen-*, TTS-CACHE-3) AND the per-button mount-warm (`<SpeakButton warmOnMount>`) are gated to them. The optional speak buttons on visual questions synthesize **on demand when tapped**, never pre-emptively (cache-warming a clip the user usually never taps was needless spend). |
| **TTS-SURFACE-2** | **Chat "Read aloud."** The long-press action menu row triggers `playTTS` for the message (practice text preferred, else native, else original) with the user's `voiceGender` (so a tutor message reads in the tutor's voice), flash-primary (TTS-ENGINE-2) at the user's speech speed. Gated off (row hidden) when the message language has no `ttsCode`. |
| **TTS-SURFACE-2a** | **Chat inline control.** `<InlineMessageTTS>` renders a `<TTSButton>` in the row gutter beside a bubble — LEFT of own bubbles, RIGHT of peers', vertically centred — configured with the SAME resolved text/language and `msg:<id>` key as the menu action, so both are one playback (no divergent text path). It's absolutely positioned so it adds no row height/width (the chat scroller is column-reverse; a per-row size change would perturb scroll geometry). Suppressed during the actions-menu lift (`!actionsAnchor`). |
| **TTS-SURFACE-2b** | The inline control is visible ONLY while THIS message's playback key (`msg:<id>`) is the active singleton key AND status is `loading` or `playing` (spinner → progress-ring + square-stop, tap = stop). Idle → renders nothing. Because playback is a singleton (TTS-CACHE-2), at most one message shows the control at a time. |
| **TTS-SURFACE-2c** | **Text ↔ language pairing.** Read-aloud resolves the `(text, language)` pair ATOMICALLY from one predicate — `resolveReadAloud` (`src/lib/readAloud.ts`): practice → native → original precedence, and the spoken language is ALWAYS the language of the exact tier the text came from. Universal content (emoji-only / URL-only / image-skip) speaks the original in its ORIGINAL language, not a viewer-language echo. BOTH the menu action (TTS-SURFACE-2) and the inline control (TTS-SURFACE-2a) MUST call this shared helper — this is what makes them "the same resolved text/language". (Fixes the wrong-language bug: text used to advance tiers on `.trim()`-emptiness while language advanced only on raw-falsiness, so a whitespace-only practice translation spoke the NATIVE text tagged with the PRACTICE voice.) |
| **TTS-SURFACE-3** | **Explain modal.** Each language card's speak button is a `<TTSButton>` on that card's text, on-demand + natural pace, with the card's language's `ttsCode`. |
| **TTS-SURFACE-4** | **Life-sim dialogue.** Each npc + user dialogue bubble carries a `<TTSButton>` speaking the bubble's practice-language text, on-demand + natural pace, gated by `ttsCode` presence. **`warmOnMount={false}`** — bubble audio is NEVER pre-warmed: a beat may never be tapped and scrolls off after ~2 turns, so synthesizing a paid clip per bubble on mount was pure waste. Synthesis happens on the FIRST tap only (playtest fix — the story used to prefetch every bubble's TTS on render). |
| **TTS-SURFACE-5** | **Vocab card.** The word card that opens under a tapped underlined word (`WordPopover`, in chat bubbles, the review dock and life-sim bubbles) carries a `<TTSButton>` at its left edge that speaks ONLY the tapped word/phrase in the practice language, key `vocab:<scope>:<word>`, **`warmOnMount={false}`** (on demand). Full contract: message-pipeline.md MSG-VOCAB-9. |
| **TTS-SURFACE-6** | **Flashcards.** Every surface that shows a flashcard's practice phrase (cards list, flip view, archived cards, card editor, practice save rows, session summary, matching tiles after answering, tutor "flashcards added" chips, Explain vocab chips) carries a `<TTSButton>` through `<CardListenButton>`, on demand (`warmOnMount={false}`). Full contract: cards-screen.md `CARDS-TTS-*`. |

## TTS-EDGE — edge cases

| ID | Case | Behaviour |
|---|---|---|
| **TTS-EDGE-1** | Both models fail (lite + flash) | Button shows brief error, returns to idle; no audio; surface unaffected (TTS-ENGINE-3, TTS-BUTTON-4). |
| **TTS-EDGE-2** | Practice language has no TTS | No listen-* questions planned (TTS-LANG-4); no speak buttons rendered (TTS-BUTTON-3); session fully playable. |
| **TTS-EDGE-3** | User switches voice preference mid-session | New calls use the new voice immediately (cache key includes gender, so no stale audio). Already-cached clips for the old gender stay cached but unused. |
| **TTS-EDGE-4** | Rapid taps across surfaces | Singleton (TTS-CACHE-2): each new play stops the prior; the active button shows stop, others return to idle. |
| **TTS-EDGE-5** | Over-long text | Cloud TTS caps `text` at ~4k bytes; the function truncates defensively and logs. (Practice/explain/chat strings are short; this guards a pathological message.) |
| **TTS-EDGE-6** | `-lite-preview-tts` unavailable (Preview model) | Only reachable as the fallback now (TTS-ENGINE-2 is flash-primary everywhere); a call where BOTH fail is TTS-EDGE-1. |

## Design decisions

- **Cloud TTS surface, not the Gemini Developer API.** The named model IDs (`gemini-2.5-flash-tts`, `gemini-2.5-flash-lite-preview-tts`) exist only on the Cloud Text-to-Speech / Vertex surface — the same surface the pre-existing `synthesizeSpeech` already used (for Standard voices). Staying on one surface keeps the request shape identical across both models, which is what makes TTS-ENGINE-3 fallback a one-field change. The Developer API has different model IDs (`-flash-preview-tts`), a different request shape, no streaming, and no `-lite` variant — out of scope.
- **All surfaces moved to flash-primary (2026-09-25).** The owner asked for every TTS call still on Flash Lite to move to Flash. The split below cost quality on the most-tapped surfaces (read-aloud, the vocab card) to save latency; the owner chose quality. Lite stays as the fallback because a Preview-only fallback is still better than no audio when flash errors. Revisit if on-demand latency complaints appear.
- **(Superseded) Model order is the user's call (split), despite equal price.** Cloud TTS prices Gemini-TTS by voice *tier*, so both models bill the same; the split (lite-primary on-demand for latency, flash-primary in practice) is a deliberate latency/quality choice, not a cost one. Fallback mitigates the Preview model's intermittent-availability risk on the on-demand hot path.
- **(Superseded 2026-09-29, audit DEAD-14) Difficulty pacing is preload-only.** Slow speech lengthens audio → more output tokens + latency. Only worth it where the clip is pre-generated and the wait is hidden (practice). On-demand stays natural to keep first-audio snappy. *Superseded by TTS-SPEED-1 (pace is a user pref on every surface); the `difficulty` and `preload` request fields were removed from the client and server together.*
- **One button, one engine.** A single `<TTSButton>` and a single Cloud Function mean the 3-state UX and any future engine change land in one place each.
