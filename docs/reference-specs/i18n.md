# i18n — UI localisation spec

> Canonical contract for the in-house localisation layer (UI chrome only — the chat-translation pipeline is a separate concern in [message-pipeline.md](./message-pipeline.md)). The store, the key-resolution algorithm, the fallback policy, and the locale-generation workflow.

Invariants are prefixed `I18N-N`; edge cases `I18N-EDGE-N`.

## Coordinates with

- [message-pipeline.md](./message-pipeline.md) — message TRANSLATION (chat content) is independent of UI LOCALISATION (chrome). Same Gemini API, different prompts, different code paths.
- [observability.md](./observability.md) — missing-key fallbacks log to Sentry as breadcrumbs (`I18N-3`).

## Domain prefix table

| Prefix | Section | Covers |
|---|---|---|
| `I18N-*` | Core contract | Store, key resolution, fallback, RTL flip |
| `I18N-GEN-*` | Locale generation | `scripts/generate-locales.mjs`, validation, commit-to-git rule |
| `I18N-EDGE-*` | Edge cases | Plural rules (or lack thereof), missing locale file, stale cache |

## 1. Core contract — `I18N-*`

| ID | Invariant |
|---|---|
| **I18N-1** | `src/i18n/locales/en.ts` is the **single source of truth**. Keys are flat (`area.screen.role` dotted form). Adding a key requires a regen run for the 80 generated locales (`npm run i18n:regen`). |
| **I18N-2** | All non-English locales are `Partial<Messages>` typed against `MessageKey = keyof typeof en`. Missing keys do NOT break the build — they fall back to English at lookup time. |
| **I18N-3** | Missing-key fallback fires a Sentry breadcrumb (`log.warn('i18n.missing-key', { key, locale })`). Coverage gaps surface in monitoring, not in user errors. |
| **I18N-4** | `useT()` is the hook for components. `tImperative()` is the non-React entry point for toasts, errors, and other call sites outside the React tree. Both go through the same store. |
| **I18N-5** | The active locale is stored in `src/i18n/store.ts` (Zustand). `setLocale(code)` dynamic-imports the locale file, merges over English, persists to `prefs(wurld:ui-locale)`, and sets `<html lang>` and `<html dir>`. |
| **I18N-6** | RTL languages (`ar`, `he`, `fa`, `ur`) flip `<html dir="rtl">` at locale-switch time, NOT per component. Tailwind's logical-direction utilities (`ms-*`, `me-*`, `start-0`, `end-0`) handle layout flips. |
| **I18N-7** | Locale files are auto-discovered via `import.meta.glob` and chunked per locale by Vite — only the active locale's JSON ships in the runtime payload. Adding a 81st locale does NOT bloat the bundle for users on other locales. |
| **I18N-8** | Locale resolution at app start: `prefs(wurld:ui-locale)` (explicit user choice) > `profile.nativeLanguage` (server-side hint) > `en` (last-resort fallback). `App.tsx` calls `initI18n` with the profile hint; explicit user choice via the picker always wins. |
| **I18N-9** | Interpolation tokens use `{name}` form. The generator preserves them verbatim — any locale where a token vanishes is dropped on the floor at generation time (`I18N-GEN-2`), never shipped. |
| **I18N-10** | **Every date/time the user reads follows the APP locale — never the device's.** `lib/time.ts` owns the chat cascade (Today / Yesterday / weekday / date); its two WORD branches resolve through `tImperative('chat.dateSeparator.{today,yesterday}')` and every DATE branch goes through `formatDate` (`i18n/format.ts`), which passes `getLocale()` explicitly. ⚠ **A bare `toLocaleDateString()`, or one passed `undefined` or `[]` as its locale, is a DEFECT, not a neutral default** — those forms resolve against the HOST locale from `navigator.languages`, which the app cannot set (there is no setter for `Intl`'s default; `<html lang>` does not feed it). That is how this shipped broken to prod and beta alike: the pill read `'Today'`/`'Yesterday'` as English literals AND formatted its dates in the device's language, so a user on an English phone with the app in Spanish got neither, and nobody developing on an English device could see it. The words and the dates fail INDEPENDENTLY and must be asserted separately — a catalogue regen fixes only the words, and the date half needs no keys at all. **Components that render these values must subscribe to the i18n store** (`messages` AND `locale`): the formatter is imperative, so React sees no dependency and the label would otherwise go stale until an unrelated re-render — invisible to any test that renders once. Asserted in `src/lib/time.test.ts` under `I18N-10`, including the intermediate state where a locale has the dates but not yet the words. |
| **I18N-11** | **The user picks the UI locale in ONE place: Settings → App preferences → App language** (`settings-app-language-row`, LANG-SET-13), which opens the shared language-picker sheet over `SUPPORTED_LOCALES` (I18N-12). It replaced the per-picker "Use as display language" radios on 2026-10-14. Not offered during profile completion. |
| **I18N-12** | *(2026-10-15, owner feedback on beta 0.3.1: the App language row was a native `<select>` while the two chat pickers above it open a sheet.)* **The App language row opens the SAME modal as "I speak" / "I'm learning"** — `LanguagePicker`, the bottom sheet with its search field, header and check mark — fed from `SUPPORTED_LOCALES` through its `options` prop instead of the chat languages. Each option is the locale's native name with the English name as its hint (`Français` · `French`), and search matches either name or the code. The row and the options carry **no flag** (a UI locale is not a country, and the row stays visibly quieter than the chat pickers above it); the sheet has no Recent row (recents are chat languages) and picking a locale never touches the chat-language recents. Choosing one calls `setLocale(code)` and the sheet closes. |

## 2. Locale generation — `I18N-GEN-*`

| ID | Invariant |
|---|---|
| **I18N-GEN-1** | `scripts/generate-locales.mjs` sends the **entire English catalogue per locale in one Gemini call** (low temperature, JSON output mode). Whole-catalogue context produces consistent register across the UI. |
| **I18N-GEN-2** | The generator validates two invariants per locale: (a) every key from `en.ts` appears in the output; (b) every `{placeholder}` token in the source value survives in the target value. Failing either invariant drops the locale on the floor for that run — silent corruption is never shipped. |
| **I18N-GEN-3** | Output is **key-sorted** so re-runs produce stable git diffs. |
| **I18N-GEN-4** | Model fallback chain (see `DEFAULT_MODEL_CHAIN` in `scripts/generate-locales.mjs`): `--model` CLI override → `gemini-3.1-flash-lite` (default primary) → `gemini-2.5-pro` → `gemini-3.6-flash`. A single model 404 does NOT sink the whole run. ⚠ **Updated 2026-09-19: the chain's tail was DEAD.** `gemini-2.5-flash` and `gemini-2.0-flash` both answer `404 "no longer available to new users"`, so what looked like four chances was two — and the invariant's own promise ("a single model 404 does not sink the run") was the thing quietly failing. `gemini-2.5-pro` still serves and stays, because a chain of near-identical models is not a fallback, it is the same failure repeated. |
| **I18N-GEN-5** | Translations are **committed to git**, NOT fetched at runtime. Zero runtime cost; reviewable in PRs; no dependency on Gemini's uptime for end-users. Re-running the generator overwrites hand edits — that's intentional; the file header tells humans the file is regenerated. |
| **I18N-GEN-6** | Cost of a regen with the default `gemini-3.1-flash-lite`: ~$0.80 for a full `--force` pass (all keys, all 80 locales) / ~$0.15 new-keys-only; tens of minutes at the default concurrency of 4. (The legacy ~$10-15 / concurrency=10 figure was the old `gemini-2.5-pro` primary — superseded.) Before running on small edits, ask the user (CLAUDE.md §Testing prompt-test guidance applies). |
| **I18N-GEN-7** | The **coined brand word "wurld"/"wurlds"** (a play on "world" — it names both the app and the "Wurlds" life-sim feature) is kept VERBATIM in every locale. Prompt rule 7 forbids translating it to the local word for "world", transliterating it, or inflecting it — in ANY case, including lowercase in-sentence uses ("start a new wurld", "how wurlds work", "your other wurlds"). Guarded by `src/i18n/localeBrandGuard.static.test.ts`; the definitive check is that "Wurld"/"Wurlds" survive the next `npm run i18n:regen`. |

## 3. Edge cases — `I18N-EDGE-*`

| ID | Edge case |
|---|---|
| **I18N-EDGE-1** | **No plural rules.** v1 strings have zero `{count} item/items` cases. When the first plural-bearing string lands, add `Intl.PluralRules` directly at the call site or behind a `tn(key, count, params)` helper — not via library machinery. If a plural-bearing string ships before that helper exists, the literal English placeholder leaks into other languages (visible bug, not a runtime crash). |
| **I18N-EDGE-2** | **Locale file missing entirely.** Dynamic-import failure (404 / network) falls back to English. The store records the attempted code so a retry can fire on reconnect, but the user keeps a usable UI in English. |
| **I18N-EDGE-2.1** | **A STALE app picking a locale recovers itself — the choice is saved first, and a failed load updates and reloads.** Owner report, 2026-09-26: "selecting a non English display language has stopped working." Cause: every locale chunk is content-hashed and kept OUT of the precache (`assets/i18n/**`, BOOT-SHELL-10), and Firebase Hosting serves only the latest deploy's files, answering any other path with `index.html` (200, `text/html`). An installed app still running an earlier bundle (the PWA's `registerType: 'prompt'` keeps it until the user accepts) therefore asks for chunk names that no longer exist, the dynamic import fails, and under I18N-EDGE-2 the choice silently stayed English — every locale the user had not already cached became unselectable after every deploy that touched a locale file, which is every regen. Now: (a) `setLocale` persists the choice to prefs BEFORE loading, so it survives a reload; (b) a failed load runs the update path (`checkForUpdateAndApply`: activate a waiting worker, then reload), and when there is nothing to apply it reloads once anyway (a plain browser tab with a stale page needs only that); (c) at most ONE recovery reload per locale per session (`sessionStorage`), so a genuinely missing file or an offline device cannot loop — it falls back to English exactly as I18N-EDGE-2 says. The reloaded app boots with the saved choice (`init` reads prefs first). |
| **I18N-EDGE-2.2** | **A stale locale chunk is a warning breadcrumb; only one that survives recovery is a Sentry error.** Sentry, 2026-10-02 (Safari): `TypeError: 'text/html' is not a valid JavaScript MIME type` from `setLocale`, right after a beta deploy that regenerated every locale chunk. That is the I18N-EDGE-2.1 case working as designed (hosting's `**` → `index.html` rewrite answers the dead chunk name with HTML), so `setLocale` logs it with `log.warn` and hands off to recovery. `recoverFromLocaleLoadFailure` calls `log.error` (`action: 'i18n.localeRecovery'`) only when the locale fails again after its one reload, or when there is no `sessionStorage` to allow one: that user is genuinely stuck in English. Offline is not reported. |
| **I18N-EDGE-3** | **Stale `prefs(wurld:ui-locale)` after a code rename.** If a stored locale code is no longer in the supported table (`src/i18n/supported.ts`), boot resolves to `en` and surfaces a one-shot toast offering to re-pick. |
| **I18N-EDGE-4** | **Dynamic / data-driven labels live OUTSIDE `en.ts`.** Not every user-facing string is a static `en.ts` key — some are generated at runtime and localised in Firestore instead. **Flashcard categories / topics** are the canonical case: Gemini classifies them at flashcard-save time, so they can't be pre-declared keys. They live in the `/topics/{id}` collection as `{ name (English canonical), translations: { <locale>: label } }`, written COMPLETE by the owner's seed script `scripts/topics-seed.mjs` (the set is closed and clients never write it — `TOPIC-SET-2/3` in [topics.md](./topics.md); **`onTopicCreate`** stays as a backstop for a hand-made doc), and rendered via `getTopicLabel` / `getTopicLabelByName` (`src/lib/topicLabel.ts`) with a `locale → base → en → titleCase(name)` fallback. **CHECK this path stays intact whenever you touch i18n, add a new dynamic-label surface, or change the supported-locale set** (a new locale needs `npm run topics:seed -- --retranslate --apply`; `UI_LOCALES` in `functions/src/prompts/topicLocalize.ts` is test-pinned to `src/i18n/supported.ts`) — a missing `translations` entry silently shows English (never an error, so it won't surface in `I18N-3` monitoring). A mirror of this note lives at the top of `en.ts` so it's seen at the point of editing. |
| **I18N-EDGE-5** | **Prose names the LANGUAGE; a picker names the VARIANT.** `localizedLanguageName(name, locale)` — default `style: 'sentence'` — KEEPS the regional qualifier, because a French UI asked for "Spanish (Latin America)" should say *"espagnol d'Amérique latine"* and `languages.test.ts` pins that. Dropping the qualifier is therefore the CALLER's decision: wrap the name in `getBaseLanguageName(...)` first. **Every mid-sentence call site must do this**, and `no-qualified-language-in-prose.static.test.ts` enforces it. `style: 'label'` calls are exempt and must stay qualified — there are FOUR English variants plus two Chinese and two Portuguese, so a picker that stripped them would offer four rows all reading "English". ⚠ Added 2026-09-21 after the owner reported *"remove things like (English (British)) to just be (English)"*: the override dialogue wraps each language in parentheses of its own, so a qualified name nested one bracket inside another. Eight of the ten prose sites already had the wrapper; two did not, which is what made this a rule rather than a fix. ⚠ The ONE deliberate exception is `ChatListItem`'s flag `aria-label`, which keeps the variant because it is the accessible substitute for the flag itself — 🇬🇧 and 🇺🇸 are different languages to a sighted user, and stripping it would remove information from the people who cannot see which flag it is. |
| **I18N-EDGE-6** | **A translated key with no caller is an UNTRANSLATED SURFACE, not dead weight.** When a component renders an English literal that also exists as an `en.ts` key, every non-English reader sees English there — and nothing reports it: the key is present, the translations are present, the lookup is simply never made, so `I18N-3` monitoring stays silent and the locale audit reports 100% coverage. **`no-orphaned-catalogue-key.static.test.ts` enforces it**: any `en.ts` value of ≥10 characters with no `t('<key>')` caller, whose exact text appears in a live source file as a JSX text node or a quoted string, fails the test. The fix is to call the key, not to delete it. ⚠ Found 2026-09-22 by an audit the owner asked for, at 18 sites — including the long-press action menu (**every** row), the delete-message confirm dialog, the deleted-message tombstone and the `edited` label. The catalogue had carried all of them, translated into 80 locales, since the keys were written. ⚠ A key with no caller AND no literal is merely dead and this rule says nothing about it; prune those when the surface that owned them goes. ⚠ Keys reached by a template literal — `t(`life.wait.${kind}`)` — have no literal caller by construction, so the guard carries an explicit prefix allowlist that must be extended alongside any new dynamic-key family. |

## 4. Design decisions

### Why an in-house layer instead of `react-i18next` / `react-intl`?

- **API surface is tiny.** A `t(key, params)` lookup + interpolation is ~30 lines. Both i18next and react-intl add 15–40 KB gzipped + provider boilerplate for things we don't need yet (plurals, nested keys, RFC 5646 negotiation).
- **No plural-rule debt.** v1 strings have zero plural cases. When we need one we'll reach for `Intl.PluralRules` at the call site — single file, no wrapper machinery.
- **Type safety.** `MessageKey = keyof typeof en` gives autocomplete + compile-time typo detection. `Partial<Messages>` for locales means missing keys fall back to English instead of breaking the build, and the fallback is logged as a Sentry breadcrumb.
- **Bundle math.** `import.meta.glob` auto-discovers locale files; Vite chunks each so only the active locale ships. No bundle penalty for the 79 we don't speak.

### Why Gemini-generated, committed to git?

- **Zero runtime cost.** The active locale is just another JS chunk.
- **Reviewable in PRs.** Hand edits are visible in diffs (overwritten on regen by design — the file header warns humans).
- **No external dependency at runtime.** End-users never hit Gemini for UI strings.

### Trade-offs

- **No plural rules.** See `I18N-EDGE-1`. Conscious deferral.
- **Translation quality is model-dependent.** The default `gemini-3.1-flash-lite` produces solid copy at a fraction of the cost of `gemini-2.5-pro` (pass `--model=gemini-2.5-pro` for a higher-quality run); neither is a native-speaker review. Strategy: ship as-is, watch Sentry's "missing key" + user reports, do a native-speaker pass per high-value locale post-launch (start with es / pt-BR / fr / de / ja / zh-CN).
- **80 locale files in `src/i18n/locales/`.** Visible directory bloat. Acceptable — they're auto-generated, deterministic, and the directory is the natural home.
- **Regen cost.** Re-running the generator is cents, not dollars: ~$0.80 for a full `--force` regen and ~$0.15 new-keys-only with the default `gemini-3.1-flash-lite` (the ~$15 figure was the old `gemini-2.5-pro` primary).

### Future work

- **Incremental regeneration** — script-level diff so adding one new key doesn't re-translate the whole catalogue.
- **Native-speaker review pipeline** — once we have user-facing locale data, route high-value pairs through a human review step before committing.
- **Plural rules** — add `tn(key, count, params)` when the first plural-bearing string lands.
- ~~**Date / number formatting**~~ — **DONE, and the deferral was the bug.** This bullet read: *"`Intl.DateTimeFormat` / `Intl.NumberFormat` are already locale-aware via `getLocale()`; wrap in `src/i18n/format.ts` once a real consumer appears (today everything goes through `lib/time.ts` which is locale-agnostic)."* `format.ts` was duly written, and `lib/time.ts` never adopted it — so "locale-agnostic" stayed true as a description while quietly becoming false as a defence: the cascade was not neutral, it was following the DEVICE. The consumer had existed the whole time, on the busiest surface in the app. Now `I18N-10`. **The transferable half: "we'll wire it up when a consumer appears" needs a named consumer, or the wrapper ships and nothing ever calls it.**
