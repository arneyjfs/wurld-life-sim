# Observability — Sentry + structured logging spec

> Canonical contract for crash reporting, structured logging, and what NOT to capture. The boundary between engineering signals (Sentry, log breadcrumbs) and product analytics (Firebase Analytics) and user-visible errors (toast copy via `errors.ts`).

Invariants are prefixed `OBS-N`.

## Coordinates with

- [cold-boot.md](./cold-boot.md) — `BOOT-QUOTA-1` writes to Sentry as breadcrumbs.
- [i18n.md](./i18n.md) — `I18N-3` missing-key fallbacks log as breadcrumbs.
- [message-pipeline.md](./message-pipeline.md) — pipeline retries / translation failures log via `log.error(err, context)` (`OBS-2`).

## 1. Core contract — `OBS-*`

| ID | Invariant |
|---|---|
| **OBS-1** | Sentry is initialised in `src/lib/sentry.ts` from `src/main.tsx`. **Captures: uncaught exceptions** anywhere in the JS runtime (React render, event handlers, promise rejections), **caught errors funnelled through `log.error(err, context)`**, and **React component errors** via the top-level `ErrorBoundary` at `src/components/ErrorBoundary.tsx`. |
| **OBS-2** | `src/lib/log.ts` is the single funnel for caught errors that the user shouldn't see. Translation-pipeline transients, image-upload retries, etc. ALL go through `log.error(err, { ...context })` — never `console.error`, never bare `Sentry.captureException`. |
| **OBS-3** | User-visible toast errors go BOTH through `pushToast` AND through Sentry: toast for the human, Sentry for the engineering log. The two paths are separate; one can ship without the other (e.g. a UX-only copy fix doesn't touch Sentry). |
| **OBS-4** | `log.info(msg, data)` and `log.warn(msg, data)` add **Sentry breadcrumbs** that appear in the lead-up to a captured error. Use them at decision points a future engineer would care about: "fired pipeline retry", "tutor chat bootstrapped", "backfill rate-limited". NOT for every render. |
| **OBS-5** | `log.setUser(uid)` runs on sign-in so Sentry events are filterable by the failing user's uid. Cleared on sign-out. |
| **OBS-6** | `toUserMessage(err)` in `src/lib/errors.ts` is the ONLY way to surface an error to the user. Translates `AppError` codes into human strings (i18n-aware). Sentry's auto-formatted error strings NEVER reach the user. |

## 2. What's NOT captured — `OBS-*` (cont.)

| ID | Invariant |
|---|---|
| **OBS-7** | **Product analytics** (DAU, retention, feature usage) do NOT go through Sentry. That's Firebase Analytics, wired in `src/lib/analytics.ts`. |
| **OBS-8** | **Network requests / performance metrics** are NOT captured — we are not on Sentry's APM tier. One sanctioned exception: `log.diagnostic` sends a single `info` message per measured event, no tracing; today only the push-tap timing (NOTIF-17.6, temporary). |
| **OBS-9** | **Session replays** are NOT captured. Privacy + cost decision. |
| **OBS-9a** | Session Replay is not merely disabled, it is **not shipped**: `src/lib/sentry.ts` imports the SDK by named members only and exposes a narrow `sentry` facade (`addBreadcrumb` / `captureException` / `captureMessage` / `setUser`; `captureMessage` since 2026-10-24, for `log.diagnostic`, NOTIF-17.6) to `log.ts`, never the `@sentry/react` namespace. Re-exporting the namespace (`export const sentry = Sentry`) defeats tree-shaking and put the Replay + Feedback integrations (~300 kB of source, rrweb) in every user's initial download even though both sample rates were 0. `scripts/bundle-budget.mjs` fails CI if an initial chunk contains the rrweb recorder (BOOT-SPLIT-5). Re-enabling replay is an OBS-9 change first; it would then load via `Sentry.lazyLoadIntegration`, never statically. |
| **OBS-10** | ⚠ SUPERSEDED 2026-10-15 by `OBS-SRV-*` (owner: server errors belong in Sentry next to the client's). Was: Cloud Functions do not use Sentry; server errors went to Cloud Logging only. Cloud Logging still receives every `console.*` line. |
| **OBS-11** | **A server write that changes a message's STATE never fails silently.** `analysis_failed` writes, and the backfill's identity-copy / strip / job-seed writes, log through `logFailedWrite` (`functions/src/pipeline/logWrite.ts`) at ERROR with `chatId` / `messageId` / `jobKey`; a failed job seed also skips that message instead of running against a job that does not exist. `pipelineFailsafeScan` logs a failed flip — the only place a stuck message becomes visible — at ERROR, and its scan summary at ERROR whenever `flipFailed > 0`. Fire-and-forget TRACE and token-usage writes keep their deliberate silent catch (OBS-TRACE: a trace must never break a send). Pinned by `functions/src/__tests__/pipelineWriteLogging.test.ts`. (Audit CPLX-FN-20.) |

## 4. Version & build provenance — `OBS-VERSION-*`

| ID | Invariant |
|---|---|
| **OBS-VERSION-1** | The **single source of version truth** is the root `package.json` `version`. Vite injects it (plus the short git SHA, an ISO build time, and the channel `beta`/`prod`/`dev`) as compile-time constants via `define` (`vite.config.ts` → `resolveBuildInfo`), declared in `src/vite-env.d.ts` and read ONLY through `src/lib/version.ts` (`frontendBuild`, `formatFrontendVersion`) — the constants themselves live in the import-free leaf `src/lib/buildInfo.ts`, which `version.ts` re-exports, so the functions fetch seam can read the version without a cycle (OBS-VERSION-9). No component hardcodes a version — the old `'0.0.0'` literals in `AboutSection`/`SettingsScreen` are gone. |
| **OBS-VERSION-2** | The **backend** version comes from the `getVersion` Cloud Function, which returns `{ version, gitSha, builtAt, channel }`. `version` mirrors `functions/package.json` (kept in lockstep with the root by `scripts/prepare-version.mjs`); `gitSha`/`builtAt`/`channel` come from `functions/buildInfo.json`, written at deploy time and gitignored (absent in local/test → graceful fallback to the package.json version + `'unknown'` + a `null` channel). ⚠ **`channel` was stored but not returned until 2026-09-22**, so the About card could say WHEN the backend was deployed but not WHICH channel it was; `prepare-version.mjs` had been writing the field all along. `SETTINGS-ABOUT-3` forbids inferring it client-side, so the row simply had no tag. `readBackendBuildInfo()` now returns it, and `null` (never a guess) when the file is absent or predates the change. ⚠ **A deployed backend keeps reporting no channel until the next functions deploy** — the file is baked into the deployed bundle, so this fix reaches the About card only when functions ship, not when hosting does. |
| **OBS-VERSION-3** | The Settings **version footer** (the About card until 2026-10-21, `SETTINGS-LAYOUT-2`) shows BOTH the frontend build (`formatFrontendVersion()`) and the fetched backend version (`formatBackendVersion()`), each with the timestamp that build landed. A **copy-debug** button copies `buildDebugInfo` — both versions, build time, channel, runtime, UID, and user agent — for sharing. ⚠ **AMENDED 2026-09-22 (`SETTINGS-LAYOUT-2`).** This used to end "…and the footer shows the frontend version line". It no longer does: the settings footer carried a second version line plus a truncated UID directly below the About card that already said both, and the owner asked for the duplicate to go. Build provenance now appears exactly once per screen. The UID is not lost — `buildDebugInfo` still carries it in full, which is the form a user can act on. |
| **OBS-VERSION-4** | **Deploying never changes the version; releasing is a commit.** ⚠ AMENDED 2026-09-29 (audit ENV-5/ENV-10) — `deploy:prod` used to bump (`--bump`) the version in the working tree *before* building, so a release version was silently patch-bumped (`0.3.0` shipped as `0.3.1`), a re-run after a failed step bumped again, and the recorded SHA never contained the version it reported. Now: (a) every `deploy:*` script runs `scripts/prepare-version.mjs` in **sync-only** mode — it mirrors the root version into `functions/package.json` and writes `functions/buildInfo.json`, nothing else; no deploy script passes `--bump` (the flag is gone). (b) **`deploy:prod`, `deploy:prod:hosting` and `deploy:prod:functions` first run `scripts/deploy-guard.mjs --channel=prod`**, which refuses (exit 1, nothing built or deployed) unless the branch is `main`, the working tree is clean, and the version is a plain release `X.Y.Z` (never `-beta`); if `HEAD` carries a `v*` tag it must be `v<version>`. The partial scripts could previously ship a `-beta` build to prod from `dev`. (c) **`deploy:prod` ships functions then hosting only**; Firestore + Storage rules (both buckets, data-boundary.md SEC-STORE-1/2) go out ONLY through `deploy:prod:rules`, which runs `deploy-guard.mjs --channel=rules` (clean tree, on `main`, `dev` or `release/*`), then `npm run test:rules` (the emulator rules suite), then `firebase deploy --only firestore,storage`. (d) Beta deploys are unchanged: sync only, no guard. (e) ⚠ AMENDED 2026-09-30 (audit ENV-4) — **`android:bundle:prod` runs the same prod guard** (a Play upload is a prod release too), and **every prod script that builds the web bundle** (`deploy:prod`, `deploy:prod:hosting`, `android:bundle:prod` and, since 2026-10-07, `ios:archive:prod` — the prod-mode App Store archive + upload, REL-8 — all with `--build`) also checks for `SENTRY_AUTH_TOKEN` in the environment or a vite env file and, when it is missing, prints a **loud warning** (`prodDeployWarnings`) and carries on: without the token `vite.config.ts` uploads no source maps and that build's prod stack traces stay minified. It is deliberately a warning, not a refusal (owner, 2026-09-30): a missing Sentry token must never block a release. `deploy:prod:functions` needs no token. Source maps are uploaded by the vite build on the owner's machine; CI does not upload them (its dead `getsentry/action-release` step, which tagged releases by commit SHA rather than `__APP_VERSION__`, is gone). ⚠ AMENDED 2026-10-15 — (e)'s "warning, not a refusal" is superseded by OBS-OPS-2: `deploy-guard.mjs --build` refuses a prod build with no resolvable Sentry token. |
| **OBS-VERSION-5** | **Between releases, `dev` carries the NEXT version as a pre-release: `X.Y.Z-beta`.** Owner, 2026-09-25: a beta build used to report the LAST prod number (so beta said "0.2.2" for months after 0.2.2 had shipped, and a stray prod-style bump on 2026-09-20 made the unreleased work look released). A numbered `-beta.1` was rejected because "the 1 means nothing". So: (a) `package.json` holds `X.Y.Z-beta` — no counter, no hash, since a commit cannot contain its own hash. (b) **Every build appends the short git SHA to a pre-release**: the displayed/recorded version is `X.Y.Z-beta.<sha>` (`buildVersion()` in `scripts/version.mjs`, used by BOTH `vite.config.ts` and `prepare-version.mjs`, so front and back agree). A release version is never decorated. (c) **Releasing a pre-release is a commit on the release branch**: `npm run version:release` applies `releaseBump('0.2.2-beta') → '0.2.2'` (and mirrors it into `functions/package.json`); the commit is merged to `main` and tagged `v0.2.2`, then deployed (OBS-VERSION-4). ⚠ AMENDED 2026-09-29: `releaseBump` of a plain `X.Y.Z` now **throws** — it used to patch-bump so a second `deploy:prod` could not re-use a number, but deploys no longer bump, and a release that needs a new number is a new pre-release. (d) **After a release, `dev` moves to the next pre-release** with `npm run version:next-beta` (`0.2.2 → 0.2.3-beta`), committed with the release. **A bigger next version** is `npm run version:next-minor-beta`: `X.Y.Z` or `X.Y.Z-beta` → `X.(Y+1).0-beta` (owner, 2026-09-26: 0.2.3 is released from a branch cut at `0.2.3-beta` while `dev` moves on to `0.3.0-beta`; the prod bump then releases `0.3.0-beta` as `0.3.0`). (e) The version line does not print the SHA twice: when the version already ends in `.<sha>`, the separate SHA segment is omitted. (f) The release commit on `main` is tagged `vX.Y.Z` and its notes live in `docs/releases/vX.Y.Z.md`; `v0.2.1` (`749297a1`, 2026-07-13) is the first tagged baseline. |
| **OBS-VERSION-6** | **Android build numbers** (added 2026-09-29, first Play upload). `android/app/wurld-version.gradle` sets `versionName` to the root `package.json` `version` verbatim (OBS-VERSION-1; no SHA, since Gradle does not share `scripts/version.mjs`) and `versionCode` to **minutes since 2020-01-01 UTC at build time**. Play refuses any upload whose `versionCode` is not higher than every earlier upload on every track, and neither semver (every beta build of `dev` is `X.Y.Z-beta`) nor a commit count (differs between `dev` and `main`) always rises; a clock does, and stays under Play's 2,100,000,000 ceiling for millennia. Both can be pinned for a rebuild with `-PwurldVersionCode=` / `-PwurldVersionName=`. Release builds are signed with the Play **upload key** from the gitignored `android/keystore.properties` when it exists (`docs/native-setup.md` §3b); Play re-signs with its app signing key. Built by `npm run android:bundle:beta` (beta functions, for internal testing) or `android:bundle:prod`. **Revisit** if two builds must be uploaded within the same minute (pin the code by hand) or if iOS wants the same scheme for `CFBundleVersion`. **iOS (added 2026-09-29, audit ENV-6)** uses the same scheme: `scripts/ios-version.mjs` stamps `MARKETING_VERSION` (→ `CFBundleShortVersionString`) and `CURRENT_PROJECT_VERSION` (→ `CFBundleVersion`) on every build configuration of both targets (App and ShareExtension — an extension's versions must equal its app's) in `ios/App/App.xcodeproj/project.pbxproj`. `MARKETING_VERSION` is the `package.json` version **without the `-beta` suffix** (`0.3.1-beta` → `0.3.1`): Apple accepts only one to three dot-separated integers there, so an iOS beta build is told apart by its build number, not its marketing version. `CURRENT_PROJECT_VERSION` is the same minutes-since-2020 clock as Android's `versionCode` (App Store Connect refuses a build number that is not higher than every earlier upload of that version). It runs as the `capacitor:sync:after` npm hook (only when the platform is `ios`), so every `npx cap sync ios` before an Xcode archive stamps it; `npm run ios:version` runs it by hand, and `--build-number=` / `--marketing-version=` pin either for a rebuild. The stamped pbxproj is a build artefact — commit it or discard it; the numbers are re-derived on every sync. |
| **OBS-VERSION-7** | **The version floor lives in Firestore at `config/version`, field `minSupportedVersion` (a semver string such as `"0.3.1"`).** It is set by the owner from the Firebase console (or Admin SDK) — never by a client and never by a deploy — so it can be raised without shipping anything. An absent doc, an absent field, an empty string or an unparseable value all mean **no floor**: a typo cannot lock every client out. Rules: `get` is public (the gate runs before sign-in, and the value is a version string, not user data), `list` and every write are denied. `getVersion` returns it as `minSupportedVersion` (`string \| null`) alongside `version / gitSha / builtAt / channel`, read **uncached** on every call — the endpoint is hit once per cold boot or long resume, and a stale answer there is exactly the lag the gate exists to remove. A failed read returns `null` (fail open). |
| **OBS-VERSION-8** | **Comparison is one pure function with a twin on each side** — `isBelowFloor(version, floor)` in `src/lib/versionFloor.ts` and `functions/src/versionFloor.ts`, parity-tested. Semver precedence on `X.Y.Z`; a pre-release sorts below its release (`0.3.1-beta.abc1234` is below `0.3.1`, per OBS-VERSION-5 the beta of a version is older than the version); two pre-releases of the same core are **not** ordered (the suffix is a git sha, which has no order), so neither is below the other. An unparseable version OR floor is never below — fail open. A leading `v` is tolerated. |
| **OBS-VERSION-9** | **Every Cloud Functions call carries `X-Wurld-Version: <frontendBuild.version>`.** The header is built once by `wurldVersionHeaders()` (`src/lib/versionHeader.ts`, a near-leaf module: the fetch seams import it, and `versionFloor.ts` imports `endpoints.ts`, so putting the header there made an import cycle that blanked the app at module init) and spread by every fetch seam: `callHttp`, `generateGemini` / `streamGemini`, the image-upload calls, the service-worker Background-Sync drain (`public/firebase-messaging-sw.js`, token `__WURLD_APP_VERSION__` injected by `firebaseMessagingSwInject`), and the native background runner (`public/background-runner.js`, mirrored alongside the functions URL by `setNativeFunctionsUrl`). `setCors` advertises the header (v2 `cors:` handlers reflect requested headers already), or the preflight would block every request. |
| **OBS-VERSION-10** | **The server rejects a call whose header is below the floor with `426 { error: "upgrade_required", minSupportedVersion }`**, before auth and before any spend. Every HTTP handler in `functions/src/index.ts` goes through `enforceVersionFloor` — v2 handlers through the wrapped `onRequestV2`, v1 handlers by an explicit call right after their method checks — asserted by `versionFloorCoverage.static.test.ts`. The floor is read through a **60-second per-instance cache** (the kill-switch pattern, LIMIT-3); a failed read keeps the last known floor, or no floor when nothing is cached. **A missing or unparseable header is ALLOWED** (`ALLOW_MISSING_VERSION_HEADER = true`): builds before this one never sent it. Rejecting a missing header is an AFTER-CHECKPOINTS job, done once the floor is at or past the first release that sends it. **Exempt:** `getVersion` (the gate must be able to read the floor from a below-floor client), `deleteAccount` + `billingDeletionCheck` (a data-rights path — App Store 5.1.1(v), GDPR Art. 17 — is never conditional on updating), and the handlers that are not in `index.ts` (billing, webhooks — see the design note). |
| **OBS-VERSION-11** | **A 426 is not an error to retry.** `callHttp` (and the Gemini seams) map it to `AppError('app/update-required')` and call `reportUpgradeRequired(floor)`, which raises the blocking screen immediately (BOOT-GATE-3) instead of waiting for the next cold boot. The page outbox keeps its normal retry path (426 is not in `TERMINAL_SEND_STATUSES`), and the two background drains treat 426 as `retry` — the entry stays queued, so a message written on an old build is sent by the updated one instead of being dropped. |
| **OBS-VERSION-12** | **The worker's build-time tokens are replaced INSIDE the worker's own build.** `public/firebase-messaging-sw.js` carries `__FUNCTIONS_URL__`, `__WURLD_APP_VERSION__` and `__WURLD_GIT_SHA__` placeholders; the replacement is a Vite plugin handed to vite-plugin-pwa through `injectManifest.buildPlugins.vite`, so it transforms the worker source in the SW build that produces the shipped file. It was a `closeBundle` rewrite of `dist/` from the app build — and vite-plugin-pwa regenerates the worker in its OWN post-ordered `closeBundle`, so the rewrite ran first and the shipped worker kept every placeholder. **Verified live 2026-10-07:** beta served `__FUNCTIONS_URL__`×2 + `__WURLD_APP_VERSION__`, prod `__FUNCTIONS_URL__`. `drainOutboxFromSW` bails when the URL placeholder is intact, so the Background Sync drain (MSG-OUTBOX-13a) had never run from a production build, and the drain's `X-Wurld-Version` (OBS-VERSION-9) would have been the literal placeholder. The source-level static test (`versionHeader.static.test.ts`) could not see this — it asserted the placeholder and the `replaceAll` call, not the output — so the OUTPUT is now checked where a build exists: `scripts/bundle-budget.mjs` (CI, every PR) fails on any placeholder in `dist/firebase-messaging-sw.js`, and `pwa-update-same-build.spec.ts` asserts the served worker. The dev-server middleware that serves the worker with tokens replaced in `vite dev` is unchanged. |

## 5. PWA update flow — `OBS-UPDATE-*`

| ID | Invariant |
|---|---|
| **OBS-UPDATE-1** | The service worker (`public/firebase-messaging-sw.js`) MUST NOT call `self.skipWaiting()` in its `install` handler. `registerType: 'prompt'` + `UpdateAvailableToast` depend on a freshly-installed SW staying in the **waiting** state so the `waiting` event fires and the "update available" banner can show. (An unconditional install-time `skipWaiting()` force-activated every update immediately — the banner never appeared, and it risked an old-page/new-SW asset mismatch mid-session.) |
| **OBS-UPDATE-2** | The new SW activates either when the user **accepts** the banner (the page posts `SKIP_WAITING`, handled by the SW's `message` listener) OR automatically on the next **cold start** once all old-SW clients have closed. So a full close + reopen always lands on the latest already-installed build with no prompt; an in-tab refresh does not reliably swap the worker. The load that first *detects* a deploy still serves the old build (it's the install) — the next cold start is the updated one. |
| **OBS-UPDATE-5** | **"Check for updates" performs a real check.** (Web and PWA. In a native shell the row asks the live-update runner, then the store: OTA-18 in [live-updates.md](./live-updates.md).) It was `location.reload()` — no `registration.update()`, no `SKIP_WAITING` — which asks the server nothing and tells the worker nothing. A reload is a NAVIGATION, the old worker is still the controller, and BOOT-SHELL-1 serves navigations cache-first from that worker's precache, so the button reliably reloaded into the build already running. *Reported 2026-07-30: "I can manually hit check for updates, which reloads, but I still need to kill the app to get it to be on the latest hash."* Killing the app worked because closing every client is the OTHER way a waiting worker activates (OBS-UPDATE-2) — the refresh path was never made to work and the kill path was quietly relied on. `checkForUpdateAndApply` does the three steps in order: `registration.update()` (the browser's own check is throttled, so an untouched install can sit on an old build indefinitely) → post `SKIP_WAITING` if that leaves a worker waiting → reload only after the new worker is in control. An `update()` that REJECTS (offline) must not report up-to-date: a worker installed on an earlier check is still applicable. Nothing waiting → no reload at all, and the user is told they are current, rather than losing their place to land on the identical build. |
| **OBS-UPDATE-6** | **The app shell must not be HTTP-cached.** Hosting matches header globs against the REQUEST PATH, and the app is requested as `/` and as SPA routes (`/chat/<id>`) that the `**` rewrite resolves to index.html. The `"/index.html"` rule matched none of those, so the shell shipped with Hosting's default `max-age=3600` — VERIFIED live before the fix: `curl -sI https://wurld-beta.web.app/` returned `cache-control: max-age=3600`. An hour-long HTTP cache on the shell defeats the update flow underneath it, because even a correctly-applied new worker can be handed stale HTML pointing at the previous build's hashed bundles. Fixed with a `**` catch-all FIRST and `/assets/**` immutable re-asserted AFTER it (hashed filenames make those safe to cache forever). **The catch-all is `no-cache`, NOT `no-store`.** `no-cache` already means "never serve without revalidating", which is the entire freshness requirement, whereas `no-store` additionally forbids STORING — including by shared caches. **MEASURED afterwards, and it did NOT deliver the saving that motivated it:** a conditional GET on `/` returns `200` with the full body (7465 bytes identity / 3050 gzip), while the same conditional GET on a hashed `/assets/*` file returns `304` with 0 bytes. So Hosting does serve conditionals — just not for this resource. The change is therefore **neutral, not an optimisation**; it is kept because `no-cache` is the conventional directive for an HTML shell and is no worse, not because it saves a transfer. Do not cite a 304 benefit here. It costs nothing either way in practice: the shell is served from the SW precache, not the network. (The bug being fixed was `max-age=3600`, which serves stale WITHOUT asking; that is a different failure from caching-with-revalidation.) `THIRD_PARTY_LICENSES.html` carries its own `max-age` because it is 2 MB and deliberately excluded from the precache, so the catch-all was the only thing governing it and it re-transferred on every visit. ⚠️ Verify with `curl -sI` on BOTH `/` and an `/assets/*` file after any hosting-header change — the failure is silent and only visible in the response headers. Also removed a dead `/version.json` rule: no such file is built, nothing fetches it, and the SPA rewrite answered it with index.html. |
| **OBS-UPDATE-3** | The SW MUST NOT `self.clients.claim()` on an AUTO-activate — only when the user accepted the update. The `SKIP_WAITING` message sets a `claimOnActivate` flag the `activate` handler checks before claiming. An unconditional `clients.claim()` let a (cold-start- or background-) auto-activated new SW seize the OPEN page before the `waiting` event surfaced, so the "update available" toast appeared only AFTER the page had silently swapped to the new build — and Accept then "reloaded the same version." | **OBS-UPDATE-4** | The "update available — reload" banner fires **IFF**: (1) a new worker is installed + **waiting** (a restart would swap the build), AND (2) the page is already **controlled** (`navigator.serviceWorker.controller` present) — so a waiting worker is a genuine UPDATE, not a first-ever install, AND (3) we have **not already prompted for the currently-loaded build** (`frontendBuild.gitSha` vs a `localStorage` marker, `SW_UPDATE_NOTIFIED_KEY`). | **OBS-UPDATE-7** | **Reload takes the SAME path as "Check for updates".** The banner's button used to call `wb.messageSkipWaiting()` on a Workbox instance that never registered (BOOT-SHELL-5) — no worker reference, so the build did not change and a second trip through Check for updates was needed to land it. It now runs `checkForUpdateAndApply` (OBS-UPDATE-5); while the apply round-trips (SKIP_WAITING out, `controllerchange` back, 3 s cap) the button shows a spinner and both buttons lock, and an outcome other than `updated` dismisses the banner as stale (OBS-UPDATE-1). |
| **OBS-UPDATE-8** | **A waiting worker of the SAME build never prompts.** `__BUILD_TIME__` is compiled into the main chunk (and the Sentry plugin stamps debug ids), so every rebuild of one commit is a byte-different worker: two beta deploys from one sha installed a "new version" that was the same version, and the banner then "updated" to an identical version line — the 2026-10-07 report *"the app updating on relaunch and then showing the prompt"*. Clause (4) of the OBS-UPDATE-4 rule: the waiting worker's git SHA must differ from `frontendBuild.gitSha`. The same comparison makes "Check for updates" (OBS-UPDATE-5) report up-to-date instead of reloading into the same build. A same-build worker is simply left waiting: it activates on the next cold start (OBS-UPDATE-2) with nothing for the user to see. E2E: `tests/e2e/specs/pwa-update-same-build.spec.ts` (`playwright.pwa.config.ts`) rewrites the built worker on disk and drives `registration.update()`. |
| **OBS-UPDATE-9** | **The banner subscribes to the REGISTRATION, not to a Workbox instance.** `UpdateAvailableToast` listened for `waiting` on a `new Workbox(...)` that never called `register()` — and workbox-window attaches its `updatefound` listener only inside `register()` — so since BOOT-SHELL-5 moved registration to `swRegister.ts` that listener was dead: a worker that finished installing mid-session (including the result of the boot-time `reg.update()`, BOOT-SHELL-3, which lands AFTER the mount-time `reg.waiting` check more often than not) never prompted until the next load, by which time a cold start had usually activated it silently (OBS-UPDATE-2) — the other half of "updated on relaunch, then prompted". ## Firestore offline-cache resilience — `OBS-FIRESTORE-*`

| ID | Invariant |
|---|---|
| **OBS-FIRESTORE-1** | iOS/WebKit can sever Firestore's IndexedDB connection on a background→foreground resume ("Connection to IndexedDB server lost"), tripping Firestore's `INTERNAL ASSERTION FAILED` (id `b815` / "AsyncQueue is already failed" / "Failed to delete record from object store") and leaving the client's async queue PERMANENTLY failed for the session — live listeners stop, optimistic sends never reconcile, direct client writes throw — until reload. Affects the Safari PWA **and** the native Capacitor WKWebView (same engine); cross-refs firebase-js-sdk #2581 / #8250. Two-layer mitigation: **(a) disable LRU GC** (`persistentLocalCache({ cacheSizeBytes: CACHE_SIZE_UNLIMITED })`, `firebase.ts`) — the GC's IndexedDB delete is the most common trigger; with it off the cache grows and the OS evicts under storage pressure. **(b) self-heal the residual** (`installFirestoreRecovery`, `firestoreRecovery.ts`): a global `error`/`unhandledrejection` listener detects the fatal signature and reloads ONCE — a plain reload re-opens the intact IndexedDB cache, so offline still loads + the connection re-establishes; if it recurs within `SAME_INCIDENT_MS` (genuine corruption, not a dropped connection) it escalates to `terminate` + `clearIndexedDbPersistence` + reload (cache wiped, re-syncs from server); after that it stops (never loops). The **outbox is unaffected** — text sends are localStorage→HTTP pipeline, image sends are a separate IndexedDB queue→`addDoc`; neither rides Firestore's cache. Decision logic is pure + unit-tested (`firestoreRecovery.test.ts`). |
| **OBS-FIRESTORE-2** | Sentry hygiene for the above (`applyEventHygiene` in `sentry.ts` `beforeSend`): the `b815` / async-queue-fatal variants collapse under one `fingerprint` (`firestore-async-queue-fatal`) + a `firestore_self_heal` tag, so the 6+ near-identical issues become a single trackable one — kept VISIBLE (not dropped) so its frequency can be monitored to decide whether to fall back to memory-cache-on-iOS. Transient `Load failed` fetch errors are DROPPED (benign network blips, non-actionable). |
| **OBS-FIRESTORE-3** | **The fatal is detected from the SDK's own error log, not only from escaped exceptions.** `installFirestoreRecovery` also registers `onLog(…, { level: 'error' })` (`firebase/app`) and runs every error-level SDK log line through `isFatalFirestoreError`. The SDK logs each internal assertion and each async-queue failure (`INTERNAL UNHANDLED ERROR: …`) BEFORE throwing, while the throw itself often lands in a promise the app handles — `useCollectionSnapshot`'s cache read ends in `.catch(() => {})`, most writes catch and toast — and so never reaches `error` / `unhandledrejection`. `INTERNAL UNHANDLED ERROR` is itself a fatal pattern: the queue is failed by ANY throw inside it (e.g. an IndexedDB `Connection … lost` DOMException), not only by an assertion. An ordinary error log (a listener's `permission-denied`) does not match. Same recovery ladder as OBS-FIRESTORE-1. Tests: `src/lib/firestoreRecovery.install.test.ts`. *(Added 2026-10-01 — see Design decisions.)* |
| **OBS-FIRESTORE-4** | **A chat list that never gets a server-confirmed snapshot is noticed within seconds and either reconnected or self-healed.** `useChatListStallWatchdog` (in `useChatsSubscription`) arms when the uid is known. If the chat-list query has not delivered a server-confirmed snapshot (`fromCache === false`) within `CHAT_LIST_STALL_MS` (3000ms), while the page is visible and `navigator.onLine` is true, it probes Firestore's LOCAL layer: `getDocsFromCache(chatListQuery)` with a `CACHE_PROBE_TIMEOUT_MS` (1500ms) timeout. The pure `decideChatListStall()` (`src/lib/chatListStall.ts`) then picks one action: **cache timed out or threw → `recover`, at once** (the client itself is wedged: its async queue or IndexedDB isn't answering local reads, which no network can fix), so it runs `recoverFromFatalFirestore` (OBS-FIRESTORE-1's ladder: reload, then clear-and-reload, never a loop); **cache answered → `wait`** until `CHAT_LIST_NUDGE_MS` (15s) after arming, then check again, and if there is still no server confirm, **`nudge`**: `disableNetwork` → `enableNetwork` re-opens the watch stream, the same nudge as a network handoff. The nudge waits because it restarts the connection: at 3s it cut off WebKit's slow first connect (the `chat-scroll-anchoring` webkit spec could not open its chat with a 3s nudge and could without one, 2026-10-18). **Server already confirmed, offline or hidden → `none`**. When it acts (`recover` or `nudge`), one `chat list stalled` error event per page load reaches Sentry with the diagnostics: decision, cache-probe result, ms since boot, cached row count, `loading`, online, visibility and whether this boot followed a killed WebView (OBS-EDGE-4). A hidden page re-arms when it next becomes visible. Tests: `src/lib/chatListStall.test.ts`, `src/hooks/useChatListStallWatchdog.test.ts`, E2E `tests/e2e/specs/chatlist-stall-watchdog.spec.ts`. *(Added 2026-10-18 — see Design decisions.)* |
| **OBS-FIRESTORE-5** | **Every recovery step that touches the Firestore client is time-bounded.** `terminate` and `clearIndexedDbPersistence` both enqueue on the async queue that has just failed, so either can stay pending forever; the clear-and-reload step races each against `RECOVERY_STEP_TIMEOUT_MS` (3000ms) and reloads whether or not they settled (`settleWithin`, `firestoreRecovery.ts`). A step that never settles must not leave the ladder latched with no reload. |
| **OBS-FIRESTORE-6** | **No hook touches a Firestore client the recovery has terminated.** The clear-and-reload step (OBS-FIRESTORE-1) calls `terminate(db)` and then waits up to `RECOVERY_STEP_TIMEOUT_MS` before reloading. In that window any component that re-renders and re-runs `useDocSnapshot` / `useCollectionSnapshot` called `getDocFromCache` / `onSnapshot` on the terminated client, which throws **synchronously** ("The client has already been terminated"), escapes the `.catch` on the promise, and reaches the ErrorBoundary as a render crash, once per re-render (WURLD-PROD-1H, 2026-10-18: 44 events plus ~107 dropped by the SDK's queue). `firestoreRecovery` marks the client shut down (`markFirestoreShutDown`, `src/lib/firestoreShutdown.ts`) BEFORE it calls `terminate`, and both hooks return early from their effect while it is set, leaving their last state on screen until the reload. Tests: `src/hooks/firestore/useDocSnapshot.test.tsx`, `src/hooks/firestore/useCollectionSnapshot.test.tsx`, `src/lib/firestoreRecovery.test.ts`. *(Added 2026-10-23.)* |


### Design decision — OBS-FIRESTORE-4 (2026-10-18)

**Trigger.** Owner report on beta 0.3.1 (iPhone native shell, 2026-10-17): *"when I load a new version my chats don't load until a restart"*, then *"it now seems to happen on native but maybe not PWA"*. In Sentry, the failing boots follow `webview terminated` (OBS-EDGE-4): the boot authenticates and then nothing. No chat-list snapshot, no listener error, no fatal log, so OBS-FIRESTORE-1/3 had nothing to fire on. A desktop-WebKit repro (persistent cache, kill the page's WebContent process, reopen) did NOT reproduce it: the list came back from the cache in ~730ms every time. So the stall's exact cause on the device is still unknown, and this invariant is built to both recover from it and name it.

**Why the cache probe is the discriminator.** With `persistentLocalCache`, a local read answers from IndexedDB through the SDK's async queue whatever the network is doing. A probe that answers means the client works and only the watch stream is stuck, so a reconnect is enough. A probe that times out means the client can't serve even its own cache, and only a reload clears that. Keying the reload on the probe, not on elapsed time, keeps a user on a slow network from being reloaded: on EDGE the server snapshot can take far longer than 3s, but the cache still answers.

**Why 3s for the wedge, 15s for the reconnect.** The owner: *"an 8s wait is a bit long to be looking at no chats"*. A healthy boot paints the list from the localStorage mirror at once and gets the server confirm in ~1s on a normal connection. The cache probe adds at most 1.5s, so a wedged client is reloading by ~4.5s. A live client with a slow server is a different case: a reconnect restarts the connection it is waiting on. The first cut nudged at 3s, and on webkit against the emulator, whose first connect takes 20–40s (`firebase.ts`, the long-polling note), every load was cut off and the chat never opened. So the reconnect is a late backstop for a stream that is truly stuck, not a speed-up.

Alternatives weighed: reload at a fixed timeout (reloads slow-network users for nothing); probe IndexedDB directly with `indexedDB.open` (tests the browser's IndexedDB, not the SDK queue in front of it, which is what OBS-FIRESTORE-1 showed failing); switch native to the memory cache (gives up offline launch and instant paint for a cause we haven't confirmed).

Revisit when a `chat list stalled` event with `cacheProbe: 'timeout'` or `'error'` arrives: that's the device evidence of the wedge, and its diagnostics say whether it followed a killed WebView.

### Design decision — OBS-FIRESTORE-3 (2026-10-01)

**Trigger.** Owner report on beta 0.3.1-beta.858a53bf (iPhone, app in the foreground, chat list on screen): after he deleted a chat and the contact, a new chat from the same person *"doesn't show at all until an app restart"*, and *"no other updates were happening"*. The whole list was frozen and the app did not reload. Every Firestore listener had stopped and the self-heal had not fired. On the emulator, chromium and webkit-mobile, with the persistent cache, the identical flow stays live (`tests/e2e/specs/chatlist-live-arrival.spec.ts`), so the freeze is not in the app's list or rules logic. A whole-client freeze that only a restart cures is the OBS-FIRESTORE-1 signature. The recovery's only detectors were global `error` / `unhandledrejection`, and the app swallows the rejections they would need.

**Alternatives.** (a) Re-throw from each swallowing `catch` — many sites, and each one would have to tell fatal errors from benign ones. (b) A watchdog that re-subscribes when no snapshot arrives for a while — a quiet chat list looks exactly like a dead one. (c) **Chosen:** listen where the SDK already reports fatals unconditionally, its logger. That is one registration and needs no call-site changes.

**Revisit if** the Sentry `firestore-async-queue-fatal` fingerprint shows reload loops (the ladder still gives up after a clear), or if the SDK ever starts logging `INTERNAL UNHANDLED ERROR` for a recoverable error.

## Pipeline traces — `OBS-TRACE-*`

The admin dashboard's waterfall is built from `pipeline.traces[]` ON THE MESSAGE
DOC (`queryPipelineTraces` reads `m.pipeline.traces`), NOT from the
`traceDetails` collection — that collection only backs the drill-down, and is
reachable only via a summary the waterfall already listed. So a stage whose
summary never lands on the doc is invisible in the dashboard even though its
full prompt + output were stored. Both invariants below exist because that
failure is SILENT by construction: `recordPipelineTrace` is fire-and-forget
with a swallowed `.catch()`, deliberately, so a trace write can never break a
user's message.

| ID | Contract |
|---|---|
| **OBS-TRACE-1** | **The message doc must EXIST before any `robustGenerate` call that names it in `traceContext`.** The trace summary is appended with `messageRef.update({'pipeline.traces': arrayUnion(...)})`; against a document that doesn't exist yet that update fails, and the failure is swallowed. Every writer that owns a message doc therefore creates a skeleton FIRST, calls the model second, and fills the doc in third. The normal tutor reply path already did this and says so at the call site; `handleTutorSetupTurn` did NOT — it generated, then created — so **every setup/onboarding message ever sent showed an empty waterfall in the admin dashboard**. Creating first is free to do and has a second payoff: the atomic `create()` becomes the concurrency lock, so a re-fired setup trigger now loses the race BEFORE spending a model call rather than after (TUTOR-SETUP-9 got cheaper as well as observable). |
| **OBS-TRACE-2** | **A writer finalising a message doc must not replace the `pipeline` map wholesale.** Use dotted-field updates (`"pipeline.state"`, `"pipeline.failsafeAt"`) so `pipeline.traces[]` survives. `handleTutorActionTurn`'s overwrite path used `ref.set(doc)` with a freshly-built `pipeline: { state: 'done', … }`, which erased the router trace AND the action-generation trace that had just been written to the same doc — so flashcard / explain / practice turns were the tutor turns that cost the MOST model calls and showed the FEWEST. There is no ordering fix available here: the traces are written fire-and-forget, so they can land either side of the final write; only a non-destructive write is safe. |

| **OBS-TRACE-3** | **A trace records the model span AND which attempt produced it.** `durationMs` is measured from inside `withRetry`'s callback, so it resets PER ATTEMPT — which makes a 15s trace ambiguous between one slow call and a retry, and those have opposite fixes. The summary now carries `attempt` (1-based) and `apiMs` (time inside `generateContent` alone, vs `durationMs` which also covers response parsing). Prompted by a real 15.6s `tutorChat` span that read like a thinking problem and was not one: measured against the same system instruction and user prompt, `thinkingLevel: "minimal"` with `includeThoughts` costs **nothing** on `gemini-3.1-flash-lite` — 1181ms median vs 1232ms with no thinking config at all, and `thoughtsTokenCount` is **0** on every call in every prompt suite (12,000+ recorded calls). Without these two fields there is nothing on the trace that distinguishes a slow model from a retried one, so the next occurrence would have started the same guess again. |

## Error coverage and labelling — `OBS-LABEL-*`, `OBS-COVER-*` (added 2026-10-15)

Added after a sweep of Sentry against every user-felt failure path (`/mnt/project-files/observability/sentry-coverage-audit.md` in the project). The rule the sweep produced: **a failure a user can feel produces exactly one Sentry event, labelled well enough to act on without reproducing it.** `log.warn` is a breadcrumb and never satisfies this.

### Labelling

| ID | Invariant |
|---|---|
| **OBS-LABEL-1** | **Every event carries the runtime.** `initSentry` sets tag `runtime` = `getRuntime()` (`native-ios` / `native-android` / `pwa-installed` / `browser`). A native WKWebView otherwise reads as "Mobile Safari" and cannot be told from a browser tab. |

| **OBS-LABEL-10** | **Expected outcomes are not errors.** A user cancelling (`auth/cancelled`, a purchase sheet dismissed), the plan gate (`feature/requires-plan`, `chat/paused`, `chat/tutor-requires-plan`) and user-input validation codes are breadcrumbs, not events. |

| **OBS-LABEL-12** | **PII keys** additionally redact `phrase`, `fileName`, `line`, `word`, `query`. `user.id` is the raw Firebase uid on purpose: the Sentry org is private to the owner and finding a reporting user's events by uid is the point (OBS-5). Extras that name a uid are still hashed. |

## 6. Design decisions

### Why deploys never bump, and why the prod guard has no override (OBS-VERSION-4)

A deploy that edits `package.json` builds from a state no commit contains: the recorded SHA is the pre-bump commit, a failed-then-retried deploy bumps twice, and a release already set to `X.Y.Z` on the release branch shipped as `X.Y.Z+1` (audit ENV-5). Making the version a commit (`version:release` on the release branch) and the deploy read-only means the tag, the build and the About card agree. The guard has no `--force`: every legitimate prod deploy is a commit on `main`, including a hotfix, and an escape hatch is exactly what the next tired deploy would reach for. An untagged `main` HEAD is allowed (tagging after a successful deploy is the owner's current habit); a *mismatched* tag is not.

### Why rules are guarded less strictly than hosting (OBS-VERSION-4 c)

Beta shares prod's Firestore and Storage, so a rule a beta feature needs must reach prod before that feature's release; requiring `main` + a release version for rules would block the beta-first flow. What matters for rules is that the deployed file is committed on an integration branch and passes the rules suite — hence `--channel=rules`: clean tree, `main`/`dev`/`release/*`, then `test:rules`. Revisit when beta gets its own project (audit ENV-1): rules then follow the hosting guard.

### Why the iOS stamp edits the pbxproj instead of an xcconfig (OBS-VERSION-6)

Both targets set `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` as target-level build settings, which override any base xcconfig, and only the Debug configuration has one. Moving them into a generated, gitignored xcconfig would need hand-edited pbxproj structure that cannot be verified off a Mac. Rewriting the two settings in place is one regex, unit-tested, and runs on every `cap sync ios` via the `capacitor:sync:after` hook. The cost is a modified pbxproj after each sync (the clock moves); it is re-derived every time, so committing or discarding it are both safe.


### Why funnel through `log.error` instead of `Sentry.captureException` directly?

- **Single grep target.** Every caught-error site is greppable as `log.error(`. If we add a new context field, redact a PII path, or swap providers, we change one file.
- **Consistent context.** `log.error` enforces the `{ ...context }` shape so every Sentry event has the same metadata structure (uid, action, surface).
- **Test-friendliness.** Unit tests mock `lib/log.ts` once; they don't reach into Sentry's internals.

### Why both toast and Sentry for user-visible errors?

The toast is for the user — short, friendly, i18n-translated copy. The Sentry capture is for us — full stack + context, never seen by the user. Same root error, two outputs, two audiences. Coupling the two (only-toast or only-Sentry) hides one or the other from a person who needs it.

### Version floor (OBS-VERSION-7..11, BOOT-GATE-*) — 2026-09-29, audit ENV-2 / DEAD-1

- **Firestore doc, not a functions constant or a hosting file.** The floor has to move without a deploy (the whole point is to stop old *native* binaries, which a deploy cannot touch), and the console is the owner's existing lever for `config/runtime` and `config/legal`.
- **The client reads it through `getVersion`, not the Firestore SDK.** At cold boot the SDK is deliberately held offline for up to 3 s (BOOT-INIT-3) and would answer from its cache, i.e. with the floor as it was the last time this device looked. A plain `fetch` to a public endpoint is independent of the SDK's boot state and fails fast offline. The rules still allow a public `get` so a future surface (the welcome site, a native pre-JS check) can read it without an endpoint.
- **`getVersion` reads uncached; enforcement reads through a 60 s cache.** `getVersion` runs about once per cold boot per device; enforcement runs on every call. A stale floor on the gate path is visible (a user keeps working on a build the owner just retired); a 60 s lag on the enforcement path is not. Cost of the uncached read: one document read per boot, less than the function invocation itself.
- **Fail open everywhere.** Offline, a Firestore blip, a malformed floor and an unparseable version string all allow. The gate is a release-safety lever, not a security boundary — a client that lies in the header is not stopped by it, and it is not meant to be. The alternative (block when the floor cannot be read) turns every outage into "everyone must update".
- **No remembered floor.** The client does not persist the last floor it saw, so a below-floor device that goes offline boots normally. Persisting it would stop that device writing old shapes offline, but the outbox cannot deliver them until it is online, where the server check (OBS-VERSION-10) refuses them anyway. Revisit if an offline write path ever bypasses the functions (a direct Firestore write that the rules accept from an old shape).
- **Missing header allowed, for now.** 0.3.0 builds in the wild do not send it. Rejecting it is recorded in AFTER-CHECKPOINTS.md with its checkpoint (floor ≥ the first build that sends it). The welcome site (`wurld.chat`) never sends it, which is safe only because the billing handlers it calls are outside `index.ts` and not enforced.
- **Billing handlers are not enforced (yet).** `stripeCreateCheckout` / `stripeCreatePortal` / `appleSyncTransaction` / `googleSyncPurchase` live in `functions/src/billing/*` and are called from the welcome site as well as the app. Enforcing them needs an allowance for the welcome site's origin; until then an old app build can still buy or restore Plus, which is harmless. Webhooks never carry the header and never will.
- **Pre-release ordering.** A beta build of `X.Y.Z` is older than the `X.Y.Z` release (OBS-VERSION-5), so it is below a floor of `X.Y.Z`. Two betas of the same core compare equal because their suffix is a sha. Raise the floor to a *released* version only.
- **Revisit** when the first App Store build exists (fill `APPLE_APP_STORE_ID` so the store button deep-links to the listing rather than opening the App Store home), or if a per-platform floor is ever needed (`minSupportedVersion.ios` etc.; today one floor covers every runtime because they ship from one version number).

### Server errors in Sentry (OBS-SRV-*, supersedes OBS-10) — 2026-10-15

OBS-10 kept functions out of Sentry to avoid a second DSN, release tagging and scrubbing. The 2026-10-15 sweep found the cost of that choice: about half the server `console.error`s logged only `err.message`, so Cloud Error Reporting did not group them; no alert policy existed; and a client "send failed" could not be put next to the server error behind it. **Chosen:** `@sentry/node` at the handler wrappers, release = backend version, `client_version` tag from `X-Wurld-Version`. **Rejected:** Cloud Error Reporting + log-based alerts only (stays split from the client's issues and releases). **Costs accepted:** a burst of identical server errors can consume quota (mitigated by a separate project, owner step, and Sentry's own rate limits); a scrubber mirroring the client's; a flush on the error path. **Revisit** if server volume threatens the plan's quota.

### Every model failure goes to Sentry (OBS-SRV-7) — 2026-10-27

**Trigger:** a translation on beta (`resolveMessageReview`, which was missing `OPENAI_API_KEY`) failed on Luna with "OPENAI_API_KEY not set", fell back to Gemini and succeeded, and Sentry saw nothing. The breaker (MSG-PIPE-31.10) only reported 3 failures within 60 s on one instance, and a rare path never gets there. **Owner's call:** report everything and judge frequency in Sentry, including transient faults, because failures that keep happening a minute apart would never open the breaker and never be seen. **Chosen:** one event per failed attempt, at the two places every model call passes through (`robustGenerate`'s attempt, `generateRouted`'s OpenAI attempt), grouped by provider + failure class so a missing key, a spending cap or an auth failure each opens its own issue (and its own new-issue alert), while transient classes are `warning`. **Rejected:** reporting only when the whole call fails (that was the gap); a per-instance throttle (it would hide exactly the frequency the owner wants to see). **Cost accepted:** a provider outage sends one event per attempt; Sentry's spike protection and the separate `wurld-functions` project bound the quota hit. **Revisit** if model failures crowd the server quota: then sample `warning`-class events, never the `error` classes.

### Coverage is enforced, not hoped for (OBS-COVER-*) — 2026-10-15

The sweep found ~217 catch sites that only `log.warn` (a breadcrumb), including every billing failure, push registration, non-OAuth sign-in and failed sends. Reviewing each call site does not stay true, so OBS-COVER-7 is a static test, and the user-felt paths are named invariants with their own unit assertions.

### Report-once rules (OBS-COVER-5/6/9) — 2026-10-15

A Firestore listener error is reported once per (hook, collection, code) per session, because the hooks re-attach every 10 s and would otherwise refile the same failure all session. App Check token failures and `parseDoc` schema drift follow the same shape: the first per session (per schema, for drift) is a `log.error`, later ones are `log.warn`. A failsafe flip to `failed` is captured every time (one event per stuck message, grouped by prior state), because each one is a user who saw a failed bubble.

### Trade-offs

- **No APM.** We don't see request timings, slow endpoints, or stalled effects directly in Sentry. The Cloud Function side has its own tracing (`PipelineTraceSummary` rows in Firestore); the admin dashboard surfaces them. If we ever need client-side perf, evaluate `web-vitals` + a separate sink before paying for Sentry APM.
- **No session replay.** Reproductions are harder for non-deterministic UI bugs. Live with it; ask users for screen recordings when needed.
