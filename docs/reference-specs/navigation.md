# Navigation (`NAV-*`)

How "back" behaves and how routes transition. Owns: `src/lib/navHierarchy.ts`
(`resolveParent`), `src/hooks/useAppBack.ts` (`useAppBack`, `useParentPath`),
`src/hooks/useAndroidBackButton.ts`, and the route-transition layer (animations).
Route tree lives in `src/routes.tsx`.

Status: **full** for the animation layer (NAV-ANIM-*, completed 2026-07) and
**full** for the back/hierarchy layer (NAV-PARENT-*/NAV-BACK-*/NAV-STACK-*,
completed 2026-09-20).

⚠ **It read "stub for the back/hierarchy layer, which is spec'd but has no
E2E" for two months, and that sentence was an accurate prediction rather than
a caveat.** In that window 16 of the app's 19 back affordances drifted to
hand-rolled `<Link>`s that pushed, and the user reported the resulting
yo-yo twice. The 43 green nav unit tests covered `resolveParent` and the
slide direction — both correct throughout — and nothing covered the callers
or the history stack, which is where all of it went wrong. **A spec that
names its own untested layer has identified the layer that will drift.**
The coverage that closes it is `tests/e2e/specs/nav-back-hierarchy.spec.ts`
(real `popstate`, which is the only place a push and a pop look different)
and `src/components/nav/backButtonGuard.static.test.ts` (the 17th hand-rolled
arrow fails the unit suite by name).

## Back = hierarchy, never history (`NAV-PARENT-*`, `NAV-BACK-*`)

| id | invariant |
|---|---|
| **NAV-PARENT-1** | `resolveParent(pathname)` returns the route a "back" climbs to, derived PURELY from the current path string — never from history. Mapping mirrors `routes.tsx`: `/chat/:id/add-member`→`/chat/:id/info`; `/chat/:id/info`→`/chat/:id`; `/chat/:id`→`/`; `/contacts/{add,new-group,edit/:id}`→`/contacts`; `/contacts`→`/`; `/cards/progress`→`/cards`; `/cards`→`/`; `/cards/practice/hub`→`/cards`; **amended 0.3.1 (PRACTICE-HUB-9):** `/cards/{practice,practice/start}`→`/cards/practice/hub` (they were `/cards`); `/wurlds/start`→`/wurlds`; `/wurlds/:worldId`→`/wurlds`; `/wurlds`→`/`; `/wurlds/overview`→`/`; `/admin`→`/settings`; `/profile/:uid`,`/settings`,`/share`→`/`; `/`→`null`. **Extended 2026-10-01 (NAV-PARENT-3):** `/chat/:id/member/:uid`→`/chat/:id/info`; `/contacts/view/:contactId`→`/contacts`; `/chat/:id/add-contact`→`/chat/:id`; and for every contact-screen path P (`/chat/:id/member/:uid`, `/contacts/view/:contactId`, `/profile/:uid`): `P/edit/:contactId`→P and `P/add-contact`→P. (`/chat/:id/info` was one until 2026-10-02, when the 1:1 info stopped rendering the contact card — CONTACTS-VIEW-6.) |
| **NAV-PARENT-2** | Unknown / unmapped paths resolve to `/` (the app root), so back is ALWAYS defined. |
| **NAV-PARENT-3** | **A screen opened from INSIDE another screen carries that screen in its PATH, so back returns to it.** Owner, 2026-10-01: *"If navigated to by clicking on a group chat member, going back should go back to the group header settings we were just on, not all the way back to the chat … this is the second nested navigation that jumps all the way back just like the photo viewer we fixed."* The hierarchy is a pure function of the path (NAV-PARENT-1), so a drill-down whose URL does not name its origin CANNOT come back to it: the member profile lived at `/profile/:uid` (parent `/`), and the `state.backTo` its caller passed stopped being read when the info screen's arrow became `BackButton` (NAV-BACK-2), so back went to the chat list. The fix is the path, never history state: the member screen is `/chat/:id/member/:uid`, the forms the contact screen opens are nested under it (`…/edit/:contactId`, `…/add-contact`), and the chat's add-contact prompt opens `/chat/:id/add-contact`. ⚠ This does NOT reopen NAV-BACK-CIRCULAR-1: a LATERAL jump to a different top-level page (chat info → media → "go to image" → `/chat/:id`) still lands on that page's own parent, because its path names no origin. Nesting is for a child whose identity includes its parent; a jump between pages stays flat. |
| **NAV-PARENT-4** | **A screen opened by a learning tip's Try it returns to the tips page** (`TIPS-TRY-2`, owner 2026-10-14: *"make sure that going back takes you back to this tutorial page"*). `resolveParent` reads ONE query marker: a URL whose query has `from=tips` resolves to `/tips`, and `from=settings-tips` to `/settings/tips`, whatever its path. Every other query is still ignored, so back remains a pure function of the URL, never of history. The tips page itself: `/tips`→`/`, `/settings/tips`→`/settings`. Callers that resolve the CURRENT location's parent (`useAppBack`, `useParentPath`, `useAndroidBackButton`, the entry stamp in `routes.tsx`, `useNavDirection`) pass `pathname + search`; `parentChain` keeps the marker on its first element only, so `parentChain('/cards?from=tips')` is `['/', '/tips', '/cards']`. `/tips` is in the chats section (`NAV-ANIM-7`). |
| **NAV-BACK-1** | Every back affordance — the in-app header arrows AND the Android hardware/gesture back (`useAndroidBackButton`) — resolves its destination through `resolveParent`, never from history. **AMENDED 2026-09-20 (`NAV-STACK-*`): the destination is still hierarchy-derived, but the MOVE is now a stack pop when `NAV-STACK-3` can confirm the entry beneath is that parent**, falling back to `navigate(parent, { replace: true })` when it cannot. ⚠ **The original text banned `navigate(-1)` outright and read "do not simplify any of these" — that ban is retired, and its reasoning is worth keeping because it was locally sound and globally wrong.** It argued `replace` stops a circular branch growing the stack (true) and keeps in-app back off the `POP` path so `NAV-ANIM-9` can mute platform pops (also true). What it missed: `replace` never SHRINKS the stack either, so the browser's own stack kept growing under a rule that believed it was preventing exactly that — and on iOS the browser's stack is the back button the user actually presses. Under `NAV-STACK-1` a pop IS the hierarchy move, so the circular-branch worry is handled by construction rather than by refusing to pop. |
| **NAV-BACK-CIRCULAR-1** | A circular route can't trap back. e.g. chat-media → image-viewer → "go to message" → `/chat/:id`: back goes to the chat LIST (`resolveParent('/chat/:id') === '/'`), regardless of the `/chat/:id/info` entry left in history. |
| **NAV-BACK-EMPTY-1** | Back NEVER lands on a blank page. A cold deep-link (push notification → `/chat/:id` onto empty history) has no history to pop, but `resolveParent` still yields a real parent (`/`), so back is always a real screen. Only at the root does Android hardware-back fall through to history / **`minimizeApp`** (**AMENDED 2026-10-02, Android sweep:** was `exitApp`, which `finish()`es the activity so the next launch is a full cold boot — splash, bundle parse, auth restore. Android 12+ moves the root activity to the back on back instead of finishing it, and users expect the app to come back where they left it; `App.minimizeApp()` is `moveTaskToBack(true)`, the same thing. Asserted in `src/hooks/useAndroidBackButton.test.tsx`). ⚠ **This was UNENFORCEABLE for the platform back button until `NAV-STACK-*`** — see below: `resolveParent` governs what the APP does, and iOS Safari's button never asks the app. |

## The history stack mirrors the hierarchy (`NAV-STACK-*`)

> **Why this section exists.** `NAV-PARENT-1`/`NAV-BACK-1` gave the app a
> hierarchy and left the browser its own history, and on iOS the browser's
> button is not interceptable — so the app had one back model and the platform
> had another, and the user met whichever they happened to press. Measured
> 2026-09-20: **19 back affordances, 3 obeyed `NAV-BACK-1`.** 43 nav unit tests
> were green throughout, because they covered `resolveParent` (correct) and the
> animation layer (correct) and nothing covered the callers or the stack.

| id | invariant |
|---|---|
| **NAV-STACK-1** | **`window.history` ALWAYS equals the parent chain of the current path.** `parentChain('/chat/A/info')` is `['/', '/chat/A', '/chat/A/info']` — `resolveParent` applied until it returns null, reversed. A forward move grows the stack by exactly one; a back move shrinks it by exactly one; a lateral move replaces from the point the two chains diverge. There is no other shape the stack may take — **with ONE exception, `NAV-OVERLAY-1` (2026-09-30): while the full-screen image viewer is open, one same-URL entry sits on top of the chain, and it is gone again when the viewer closes.** |
| **NAV-STACK-2** | **Therefore "history back" and "hierarchy back" are the SAME operation** — which is the entire point, and the only way the platform button can be correct. iOS Safari's back is a raw `POP` the app cannot veto (nothing in `src/` listens to `popstate`, and a `preventDefault` does not exist for it). `NAV-BACK-1`'s `replace` discipline can never fix it: **`replace` cannot create an entry BELOW the bottom of the stack**, so a deep-linked entry stays the floor no matter how disciplined every in-app affordance is. Making the stack equal the chain is what removes the second model rather than trying to out-argue it. |
| **NAV-STACK-3** | **The invariant is CONFIRMED at runtime, never assumed.** Every entry carries `navDepth` in `history.state`. A back affordance pops only when the depth proves the entry beneath is the parent; when it cannot be confirmed — a foreign entry, a restored session, a state this code did not write — it falls back to `navigate(parent, { replace: true })`, the old `NAV-BACK-1` behaviour. **A stack invariant with no runtime check is a comment**, and this one is edited by the browser, other tabs, and session restore. |
| **NAV-STACK-4** | **Boot seeds the chain.** On a cold load at any non-root path — push-notification deep link, refresh, pasted URL — the app `replaceState`s the root and then `pushState`s each descendant down to the current path BEFORE the router renders, so the platform back has real parents beneath it. The current entry keeps the arrival URL's query and hash; the ancestors carry neither (fixed 2026-09-24: the seed pushed the bare pathname, which dropped `/share?inbox=…` and every other query-carrying deep link before React ran). **Accepted cost, stated plainly: leaving the app from a deep link now takes N presses instead of 1.** That is the trade the bug demanded — "back took me to an empty Safari page" is the report, and the only alternative to seeding is leaving the deep-linked entry as the floor. |
| **NAV-STACK-5** | **The path the app booted on is in history exactly ONCE.** A deep link is already on screen after `NAV-STACK-4` seeds it, so anything that "routes to" that same path at boot — the push-tap intake (`installPushTapListener` captures the chat id from the launch URL, which it needs for the signed-out case) — must NOT push it again. The pending-nav effect in `App.tsx` navigates only when the target differs from the current path; when they are equal it just clears the pending id. *(Owner report 2026-09-25, iOS PWA: "it opens to the chat. Navigating back … lands on the chat again, going back again lands on the empty page." The duplicate was `[/, /chat/x, /chat/x]`: a PWA-only path (`isPwaOrNative()`), so no E2E ran it.)* |
| **NAV-STACK-6** | **In the iOS home-screen app, back can never leave the app** — the catch-all. iOS standalone has no browser chrome and no "back to exit" convention: popping past the app's first entry lands on a blank Safari page, which is never what the user meant. So when `canLeaveAppViaHistory()` is false (iOS standalone web app only), boot puts a **guard** entry (`/`, marked `wurldNavGuard`) BENEATH the seeded chain, and a `popstate` that lands on the guard immediately pushes a fresh `/` above it: the user sees home, and home stays home however often they swipe back. **Why a guard under the chain rather than trusting the chain's own root:** iOS may skip history entries a script created before any user interaction, and whether it did is exactly what the report cannot tell us — the guard is the one entry made by `replaceState` on the arrival entry, which is never "created", so it is reachable in either model. **Scope, deliberately narrow:** a browser tab keeps normal back (people genuinely navigate away on the web); the Android installed app keeps back-at-home-exits-the-app (that IS its convention); native builds own back through `useAndroidBackButton`. Message links open outside this history (`target="_blank"`), so they are unaffected. |
| **NAV-BACK-2** | **Exactly ONE back affordance implementation.** Every back arrow in the app renders the shared component; a hard-coded `<Link to="…">` back arrow is a defect, not a shortcut. This is the rule whose absence produced the drift: `useAppBack` was correct, tested, and used by 3 screens out of 19, and nothing — no lint rule, no test, no E2E — noticed the other 16. **`useAppBack` being right is worth nothing while 16 screens don't call it**, so the enforcement is part of the invariant, not a nicety. |

## Native shell back gesture (`NAV-NATIVE-*`)

| id | invariant |
|---|---|
| **NAV-NATIVE-1** | **On the native iOS build, the left-edge swipe goes back** (owner, first native build 2026-10-02: *"swipe back doesn't work between pages"*). `MainViewController` sets `allowsBackForwardNavigationGestures = true` on the Capacitor WKWebView, which is the same interactive back/forward swipe Safari and the home-screen PWA give the app. It needs nothing else from the app because `NAV-STACK-1` already makes `window.history` equal the parent chain: the swipe performs a `POP` to the parent, which `NAV-ANIM-9` does not re-animate, the image viewer's own entry (`NAV-OVERLAY-1`) makes the swipe close the viewer, and at the root there is no entry beneath, so the swipe does nothing (a native app cannot be left by swiping). Android keeps its system back via `useAndroidBackButton` (`NAV-BACK-1`, `NAV-OVERLAY-2`). Asserted statically (`src/notifications/iosNativeWiring.static.test.ts`); the gesture itself is a device check (`docs/ios-device-checklist.md`). **Known cost, unchanged from the PWA:** WebKit shows its snapshot of the parent page during the drag, taken when the user left it, so a list that changed meanwhile updates when the swipe lands; a sheet open on the page is left with the page (`NAV-OVERLAY-2`'s stated cost). **Trigger to revisit:** reports of a stale or blank snapshot mid-swipe — then replace it with an app-driven interactive edge pan over the two-slot transition (`NAV-ANIM-2`), which can show the live parent. |

## Full-screen overlays (`NAV-OVERLAY-*`)

| id | invariant |
|---|---|
| **NAV-OVERLAY-1** | **Back from the full-screen image viewer closes the viewer and lands on the screen it was opened from** (owner, 2026-09-30: *"Going back from the image viewer should go back to the chat, not back to the chat list"*). The viewer is an overlay, not a route — `resolveParent` has no entry for it and `NAV-PARENT-1` is unchanged — so it carries its OWN history entry: on open it `pushState`s one entry with the SAME URL and a copy of the current state plus `wurldViewer: <token>` (`src/lib/viewerHistory.ts`). A `popstate` off that entry closes the viewer; the path did not change, so the router keeps the page mounted (same-path slot, `NAV-ANIM-1` returns `null`, nothing animates). Android native back (`useAndroidBackButton`) pops the viewer entry before it considers the hierarchy. Closing the viewer any other way pops the entry if it is still current, so the stack returns to exactly the `NAV-STACK-1` chain and the NEXT back climbs the hierarchy as before (chat → list). A navigation fired from inside the viewer (the gallery's "Go to message", `NAV-BACK-CIRCULAR-1`) `replace`s the viewer entry, so it never survives under the page it navigated to. Asserted by `tests/e2e/specs/image-viewer-fit-back.spec.ts` and `src/lib/viewerHistory.test.ts`; the viewer side is `IMG-VIEWER-11` in image-messages.md. |
| **NAV-OVERLAY-2** | **The Android back button closes the topmost open sheet, dialog or in-page step before it considers the page** (owner, 2026-10-01: *"The Android back button doesn't close bottom sheets."*). A process-wide, in-memory **overlay back stack** (`src/lib/overlayBackStack.ts`) holds one close callback per open overlay, most recent last; an overlay registers while it is open through `useOverlayBack(open, onClose)` (`src/hooks/useOverlayBack.ts`) and unregisters when it closes or unmounts. `useAndroidBackButton`'s order is: (1) NAV-OVERLAY-1's viewer entry; (2) **`closeTopOverlay()`** — when anything is registered it calls the TOP callback and the press is consumed: the URL does not change; (3) only then the hierarchy climb (`NAV-BACK-1`). The callback is the overlay's OWN cancel/close path (the same one its × / scrim / Escape uses), so a guarded close (a send in flight, a save in progress) stays guarded and back is then a no-op rather than a page exit. **Registered:** `BottomSheet` (and with it `ConfirmDialog` and every sheet built on it), `CountryDialPicker`, `MessageActionsMenu`, `TranslationFeedbackModal`, `EditOverlay` (back cancels the edit), `ImagesReviewModal` (back = its × / Stop), `CircleCropModal`, `CardEditorSheet`, `ChatImportModal` (not while saving), the Life screen's `VocabPopover`, `AvatarModal`, `GoalChip` sheet and the two delete-confirm dialogs (`WorldCard`, `LifeScreenMenu`; not while deleting), and the in-page wizard steps that replace a screen without a route: the `LANG-FREE-13` language step (`FreeChatLanguageStep`, back = its header arrow: cancel the pending chat / return to the group's name step) and `CreateGroupScreen`'s name step (back = the member picker). **Not registered, deliberately:** the image viewer (it has NAV-OVERLAY-1's history entry, which already wins at step 1), and `WorldIntroScreen` / `WurldResumeScreen` (forward-only gates with no cancel — back leaving the page is the only way out). **Scope: Android NATIVE back only.** Browser / PWA back and the iOS edge swipe are raw `POP`s the app cannot veto (`NAV-STACK-2`), so with a sheet open they still leave the page — see the Design decision. E2E seam: in an `E2E_TEST_BUILD` the hook also answers a `wurld:e2e-backbutton` window event with the same handler. Asserted by `src/lib/overlayBackStack.test.ts`, `src/hooks/useOverlayBack.test.tsx`, `src/hooks/useAndroidBackButton.test.tsx`, `src/components/ui/BottomSheet.test.tsx`, `src/components/Chat/FreeChatLanguageStep.test.tsx` and `tests/e2e/specs/android-back-overlay.spec.ts`. |

## Beta-gated sections (`NAV-BETA-*`)

| id | invariant |
|---|---|
| **NAV-BETA-1** | **A section gated on a beta flag is UNREACHABLE while that flag is off — the tab AND the route.** The tab half is `NAV_TABS[].betaFlag`, filtered identically by both renderers (`TabBar`, `NavRail`) so one form factor cannot keep a hidden surface reachable (`UI-DESKTOP-5`). The route half is `BetaRouteGate` (`components/nav/BetaRouteGate.tsx`) wrapping every route element in the section, INCLUDING its legacy-redirect aliases: with the flag off the gate renders `<Navigate to="/" replace />`. **Not rendering the tab is not a gate** — `/wurlds` is also a typed URL, a bookmark, a push deep-link, and a path `NAV-STACK-4` seeds the history stack from at boot. |
| **NAV-BETA-2** | The gate **redirects to `/`**, it does not render a 404 or an empty screen. Rationale: `NAV-PARENT-2` already resolves every unknown path to `/` and `NAV-BACK-EMPTY-1` forbids landing on a blank page; a flagged-off route is exactly an unknown path from the user's point of view, so it gets the same answer the route table's `*` case gives. `replace` (not push) keeps the stack equal to the parent chain (`NAV-STACK-1`) — a gated entry must not become something back can return to. |
| **NAV-BETA-3** | The gate does NOT change `NAV_SECTIONS`, `resolveParent` or `parentChain`. Those stay pure functions of the path string (`NAV-PARENT-1`) — a gate that edited the hierarchy would make "back" depend on a localStorage flag, and `NAV-ANIM-7`'s section order would shift under the tab bar when a flag flipped. The gated section keeps its index and its parent rules; it simply has no reachable page while the flag is off. |

Which flag gates which section is NOT declared here — it is `TAB_CHROME` in
`components/nav/navTabs.ts` (presentation) plus the route wrappers in
`routes.tsx`. Today: `wurlds` ← `lifeSimBeta` (`SETTINGS-BETA-4`,
[settings-screen.md](./settings-screen.md)).

Tested: `src/components/nav/BetaRouteGate.test.tsx` (redirect + the static
check that the real route table wraps every `/wurlds*` and `/life*` route),
`src/components/nav/navTabs.test.ts`, `src/components/nav/NavRail.test.tsx`,
`src/components/TabBar.test.tsx`, `tests/e2e/specs/wurlds-beta-gate.spec.ts`
(`@standard` — the post-condition that matters: with the flag off, a direct
`goto('/wurlds')` ends up on `/`).

## Route transitions / animations (`NAV-ANIM-*`)

| id | invariant |
|---|---|
| **NAV-ANIM-1** | **EVERY navigation the APP performs animates** (the one exception is a platform-driven `POP` — NAV-ANIM-9). Direction is classified by STRUCTURE, not history — mirroring NAV-PARENT-1 — by `useNavDirection(pathname, navigationType)`, first match wins: (a) `forward` when `resolveParent(current) === prev` (`/` → `/chat/:id`, `/chat/:id` → `/chat/:id/info`); (b) `back` when `resolveParent(prev) === current` (`/chat/:id` → `/`); (c) for a PEER move — neither is the other's parent — compare `resolveSectionIndex` (NAV-ANIM-7): a later section is `forward`, an earlier one is `back` (`/contacts` → `/cards` slides in from the right; `/cards` → `/contacts` from the left); (d) any remaining peer — same section, or a route outside the section list — defaults to `forward`. `null` ONLY for first render, for a pathname that didn't change, and for a `POP` (NAV-ANIM-9). Apart from the `POP` gate every rule is a pure function of the two path strings, so the slide stays consistent with where "back" would go. |
| **NAV-ANIM-7** | Section order is `NAV_SECTIONS` in `lib/navHierarchy.ts` — ONE ordered, pure list of the app's top-level destinations (`/` → `/contacts` → `/cards` → `/cards/practice/hub` → `/wurlds` → `/settings`; the practice section added 2026-10-24, NAV-PRACTICE-1), each with the predicate that decides whether a path belongs to it (`/chat/:id` is in the chats section; `/cards/practice/start` is in practice). `resolveSectionIndex(pathname)` returns its index, or `-1` for a route in no section (`/profile/:uid`, `/admin`, `/share`). `NAV_TABS` (`components/nav/navTabs.ts`) DERIVES its `matches` predicates and its order from this list rather than declaring its own, so the animation direction and the tab bar's left-to-right order cannot drift — a tab reordered in the bar reorders the slide with it. The list lives in `lib/` and holds no React (the tabs' icons/labels/beta-flags stay in `navTabs.ts`). `isChatSection` is `resolveSectionId(p) === 'chats'`. |
| **NAV-ANIM-2** | A navigation mounts BOTH pages. `AnimatedRoutes` (routes.tsx) keeps a list of up to 2 "slots", each rendering the route table at its OWN location, keyed by a STABLE id. On any navigation with a direction (which since NAV-ANIM-1 is all of them) the current slot is kept (now exiting) and an entering slot is added — stable ids mean the OUTGOING page keeps its LIVE React instance and animates out as itself (no blank remount). The INCOMING page slides in: from the RIGHT on `forward`, from the LEFT/receded on `back`. Direction comes from `useNavDirection`, which lives in the PERSISTENT parent (its prev-pathname ref survives across the slot mounts). Pure state-machine core: `reduceNavSlots` (`lib/navTransition.ts`). Classes: `.page-anim-{enter,exit}-{forward,back}` — transform/opacity only, `both` fill so the exit page holds its final frame until dropped (`PAGE_ANIM_MS` after the nav). Duration + curve are NAV-ANIM-6. `null` direction → instant single-slot swap. |
| **NAV-ANIM-3** | PARALLAX (supersedes the former incoming-only design — the owner's "old page should stay or smoothly move out" request). On `forward` the outgoing parent RECEDES (`translateX(-22%)` + dims to 0.6) BEHIND the incoming child; on `back` the outgoing child slides fully OFF to the right ON TOP, while the revealed parent returns from its receded/dim state (reverse parallax). Z-order puts the covering page on top (`navSlotZIndex`: forward-incoming / back-outgoing = 20, the other = 10). Keeping two route trees mounted for `PAGE_ANIM_MS` is the cost the old design avoided — accepted here because the outgoing slot reuses the LIVE instance (stable id), so even the delicate ChatScreen animates out without a remount/flash. Steady state renders a SINGLE slot in normal flow (`flex-1 min-h-0`); ONLY mid-transition are both slots `absolute inset-0`. |
| **NAV-ANIM-4** | All platforms — app-level CSS, not a native page transition. Transform/opacity only keeps it WKWebView-safe. `prefers-reduced-motion: reduce` disables the slide AND skips the dual-mount (instant single-slot swap via `reduceNavSlots(..., reduce=true)`), so reduced-motion never lingers the old page on `back`. |
| **NAV-ANIM-6** | ONE duration, ONE curve, declared ONCE. `PAGE_ANIM_MS` (exported from `lib/navTransition.ts`) is the single source of truth for how long a page transition lasts; the four `.page-anim-*` rules in `globals.css` MUST all declare that same duration, because the JS timer is what drops the outgoing slot and a CSS animation that outlives it gets cut off mid-frame (and one that finishes early leaves the old page parked on screen). Value: **380ms** on `cubic-bezier(0.33, 0.1, 0.2, 1)`. The transition used to run 280ms on `cubic-bezier(0.32, 0.72, 0, 1)` — an iOS-style curve so front-loaded that ~70% of the travel is spent in the first ~25% of the time, which combined with the short duration read as a FLASH rather than a push (owner report, 2026-07). The replacement keeps an ease-out finish but gives the motion a real ramp-in, so the eye tracks the page instead of catching only its arrival. The parallax depth + dim (NAV-ANIM-3) are unchanged; the extra 100ms is what makes them legible. Asserted by `src/styles/globals.pageAnim.test.ts` (CSS ↔ constant sync + the floor below which the transition reads as a flash). |
| **NAV-ANIM-9** | **A platform-driven `POP` does NOT animate.** `useNavDirection` takes React Router's `useNavigationType()` and returns `null` — an instant single-slot swap (NAV-ANIM-2), no dual mount — whenever it is `POP`, whatever the path structure would otherwise have said. Rationale: a `POP` can ONLY come from the browser/OS back-or-forward affordance (iOS edge-swipe, Android predictive back, browser chrome), which has ALREADY run its own interactive transition by the time `popstate` fires. Replaying `.page-anim-enter-back` on the page the platform just settled restarts it from `translateX(-22%)` + dim and slides it in a SECOND time, which the eye reads as overshoot-and-bounce (owner report 2026-07-31: "swiping back from a page with a lot of speed causes the page below to bounce"). This CANNOT silence an in-app back affordance: NAV-BACK-1 requires every one of them to `navigate(parent, { replace: true })` — a `REPLACE`, never a `POP` — so the header arrow and the Android hardware back keep their slide. The single `navigate(-1)` NAV-BACK-1 permits (the root-level fallback in `useAndroidBackButton`) is a raw-history hop with no hierarchy meaning and is deliberately covered by this rule. **AMENDED 2026-09-20 (`NAV-STACK-*`).** In-app back is now a stack pop, so it DOES arrive as a `POP` and this gate would have silenced it — the exact regression the old text warned about, arriving by the door it was holding shut. The gate now distinguishes an APP-INITIATED pop from a platform one: the back affordance raises a module flag immediately before calling `go(-1)`, and `useNavDirection` consumes-and-clears it, treating that one `POP` as a hierarchy move (animate) and every other `POP` as the platform's (do not). The flag is consumed exactly once so a platform pop arriving later can never inherit it. ⚠ **The old sentence read: "NAV-BACK-1 is therefore load-bearing for NAV-ANIM-9 — a back affordance rewritten to `navigate(-1)` would silently lose its animation."** It was right, and it is the reason this amendment exists rather than being discovered as a visual bug later. |
| **NAV-ANIM-10** | **Direction classification is idempotent under render replay.** `useNavDirection` is called in render, and React may render `AnimatedRoutes` more than once for ONE navigation and commit only the last pass: React Router 7 delivers every navigation inside `startTransition`, a transition render is interruptible (any urgent update mid-render — a Firestore snapshot, a scroll handler — discards the work and re-renders), and StrictMode double-renders every pass in dev. So nothing in the classification may MUTATE shared state in render. The app-initiated-pop mark (NAV-ANIM-9 amendment) is therefore **peeked, never consumed, in render**: `markAppInitiatedPop(from, to)` records the move the back affordance is about to make; render asks `isAppInitiatedPop(prev, pathname)`, a pure read that matches only that exact move; the mark is cleared in `useNavDirection`'s post-commit effect on the next committed pathname change (so a platform `POP` arriving later still cannot inherit it — the consume-once guarantee, moved from the render to the commit). Observable contract, asserted frame-by-frame in E2E: **an in-app back arrow from a chat to the chat list ALWAYS co-mounts both slots, the chat slides off monotonically while the list returns from its receded position, and every frame that shows the list shows it populated (never the Suspense fallback, never an empty list).** Found 2026-09-30 from the owner's beta report "occasional small flicker coming from a chat BACK to the chatlist" — see Design decisions. |
| **NAV-ANIM-12** | **A pushed page is on screen only where its own slide puts it.** In every frame of a transition, each slot's on-screen position equals its `.page-anim-*` transform — the incoming page is never shown early and the outgoing page never leaves early. The slot area therefore CLIPS (`.nav-slots`: `overflow: clip`, `overflow: hidden` + a scroll reset as the fallback where `clip` is unsupported): the incoming slot starts at `translateX(100%)`, i.e. entirely in the scrollable overflow of whatever contains it, and a page that focuses a field on mount (`autoFocus` on `/contacts/add`, `/contacts/edit/*`, the new-group name, the chat-info rename) made the browser scroll the nearest scrollable ancestor — `#root`, which is `overflow: hidden` but still programmatically scrollable — sideways to reveal it. ## Design decisions

- **Parent-from-path, not history.** The owner's requirement ("back goes to the
  higher page in the hierarchy, not the previous page" + "never land on an empty
  page"). A pure path→parent function is deterministic, unit-testable, and
  immune to history state (cold deep-links, circular routes). The cost: back is
  not literally "undo the last navigation" — but for this app's tree that's the
  desired product behaviour.
- **`replace` everywhere.** Prevents stack growth on circular branches and the
  back-into-the-previous-chat bug after a notification open.
- **`/admin`'s parent is `/settings`, not `/` (2026-09-20).** Found while
  converting the 16 hand-rolled arrows to `BackButton` (NAV-BACK-2). `/admin`
  is only ever reached from the admin row on the settings screen
  (`screens/Settings/FooterLinks.tsx`), and both of its header arrows were
  hard-coded `<Link to="/settings">` — so the arrow went to Settings while
  `resolveParent` sent the Android hardware back to `/`. **Two back
  affordances, same page, different destinations**, which is exactly the
  divergence NAV-BACK-1 exists to make impossible; the hand-rolled arrow was
  hiding it, because a `<Link>` never consults the resolver. Deriving the
  arrow from `resolveParent` forces the question, and Settings is the honest
  answer: `parentChain('/admin')` is now `['/', '/settings', '/admin']`, so
  the seeded stack (NAV-STACK-4) contains the screen the user actually came
  from. Consequence on the animation layer: `/admin` → `/` is no longer a
  hierarchy `back` (it climbs two levels at once) and falls through to the
  peer default, `forward` — `/admin` belongs to no section (NAV-ANIM-7) so
  there is no order to rank it by. Nothing in the app makes that move: the
  arrow and the hardware back both go to `/settings` now, and `/` is only
  reachable from there by a tab tap. `/settings` and `/share` keep `/`.
- **Every navigation animates; peers read their direction off the section order
  (2026-07).** NAV-ANIM-1 originally left peers and tab switches at `null` — an
  instant swap — on the reasoning that a lateral move has no "depth" to
  express. In use that just read as half the app being unanimated: `/` ↔
  `/contacts` slid (root IS the parent of every section, so those are
  hierarchy moves), while `/contacts` ↔ `/cards` cut instantly. The owner asked
  for the missing ones, sliding in from the right with back reversing it.

  Taking "all slide in from the right" literally would have made `/cards` →
  `/contacts` slide in from the RIGHT while `/cards` → `/` (one tab further in
  the same direction) slides in from the LEFT — the same leftward gesture on
  the tab bar producing opposite animations depending only on whether the
  target happens to be the first tab. Reading the direction off the section
  order instead makes the root case a special case of the general one: moving
  right along the bar always slides in from the right, moving left always from
  the left, and the existing `/` ↔ section behaviour falls out unchanged. The
  requested default still governs everything the order can't rank — two chats,
  two practice sub-screens, a route outside the section list — which all slide
  in from the right.

  Cost: a tab switch now co-mounts two route trees for `PAGE_ANIM_MS`, where
  before it swapped one. That was already the accepted price for hierarchy
  navigation (see the parallax note below); this extends it to lateral moves.
  Reduced-motion still skips the dual-mount entirely (NAV-ANIM-4).

- **Parallax over incoming-only (2026-06-19).** The first cut animated only the
  incoming page (NAV-ANIM-3, old form) and the keyed-remount unmounted the
  outgoing tree instantly, so the old page went *blank* during the slide. The
  owner asked for the old page to stay / move out smoothly. Resolving that
  required reversing the deliberate "don't mount two trees" call. The risk it
  guarded against (a heavy screen like ChatScreen mounted twice + a blank
  remount of the outgoing page) is avoided by the **stable-id two-slot
  machine**: the outgoing slot keeps the SAME React instance it had before the
  nav, so it animates out as its live self — no second mount, no blank. Both
  trees are co-mounted only for the `PAGE_ANIM_MS` transition, and reduced-motion +
  peer/tab switches skip the dual-mount entirely. Device pass on iOS PWA (the
  ChatScreen scroll engine surviving the absolute↔static reflow at transition
  start/end) is the first-run check.

### NAV-PARENT-3 — a drill-down's origin lives in its path (2026-10-01)

**Report.** Owner: back from a group member's screen went *"all the way back to
the chat"* (on the device: past the chat, to the list) instead of to the group
info it was opened from — *"the second nested navigation that jumps all the way
back just like the photo viewer we fixed."*

**Root cause.** The member screen was `/profile/:uid`, and
`resolveParent('/profile/:uid') === '/'`. `MemberRow` passed
`state={{ backTo: '/chat/:id/info' }}`, `ProfileScreen` read it and passed it
on, and `OneToOneInfo` handed it to `Shell` — which, since NAV-BACK-2 made its
arrow `BackButton`, takes no `backTo` at all. The prop was dead; the arrow (and
the platform back, which never asks the app) went to the hierarchy parent of a
path that did not name the group.

**Alternatives weighed.**
- *Honour `state.backTo` in `BackButton`.* History state is per entry and dies
  on a reload or a cold deep link, and the platform back never reads it — it
  would reintroduce exactly the two-back-models problem NAV-STACK-1 removed.
- *A `resolveParent` that consults history.* Contradicts NAV-PARENT-1 and
  reopens NAV-BACK-CIRCULAR-1.
- *Put the origin in the path* — chosen. `/chat/:id/member/:uid` is a child of
  `/chat/:id/info` in the same pure function as everything else, the seeded
  stack (NAV-STACK-4) has the group info beneath it on a cold load, and the
  platform back agrees with the arrow for free. Cost: one person has several
  URLs (one per place you can open them from), and every form the screen opens
  needs a nested twin route (`…/edit/:contactId`, `…/add-contact`) — the
  route table grows by ten lines, `resolveParent` by four rules.

identity includes its parent (this member, *of this group*). A jump to a
different page — chat info → media → "go to image" → `/chat/:id` — lands on a

asserted by `image-viewer-fit-back.spec.ts` and `navHierarchy.test.ts`.

### NAV-ANIM-8 — a redirect-only section root does not re-animate

A tab whose `to` is a bare section root that only redirects makes ONE tap into TWO navigations, and the second overwrites the first's direction with the `from === to` default.

Reported 2026-07-31: "Going from settings page to Wurlds page is the wrong animation order." The Wurlds tab points at `/wurlds`, which is `<Navigate to="/wurlds/overview" replace />`. So `/settings` → `/wurlds` ranks correctly as **back** (settings 4 → wurlds 3), and then `/wurlds` → `/wurlds/overview` lands in the SAME section, falls through to the peer default, and re-animates **forward** — the page visibly slid the wrong way.

**The root cause is fixed rather than guarded around**: the overview now lives AT `/wurlds`, and `/wurlds/overview` is the redirect (so old links and bookmarks still resolve, but nothing in the app routes through it). A tab's `to` must be a real destination — that is what the ranking model assumes.

The guard stays as the general rule it should always have been: a hop through a redirect-only section root has no left/right of its own, so it resolves to `null` and leaves the first animation running rather than fighting it. Only the bare root counts (`NAV_SECTIONS[].to`), and `/` is excluded — it is a real destination. **Nothing in the app exercises it today**; it exists so the next tab that gains a redirect root does not reintroduce the bug.

### NAV-ANIM-9 — the platform's back gesture animates once, not twice

Reported 2026-07-31: "swiping back from a page with a lot of speed causes the page below (incoming) to bounce (keep incoming momentum, overshoot and animate a bounce back)."

This **contradicted NAV-ANIM-1 as written** ("EVERY navigation animates"), and the owner asked for the change, so the invariant is amended rather than worked around.

The bounce is not an overshoot in the curve — `cubic-bezier(0.33, 0.1, 0.2, 1)` has every control point inside `[0,1]`, so a single `translateX` keyframe on it mathematically cannot overshoot. It is a **double animation**. The app has no back-swipe gesture handler of its own; the swipe is the platform's, and WebKit (iOS Safari / standalone PWA) drives it from a page SNAPSHOT, interactively, with the gesture's own momentum. When the gesture commits, the platform has already finished — the previous page is settled on screen. THEN `popstate` fires, React Router publishes the new location, `useNavDirection` classifies the move as `back` off the path structure alone, and `.page-anim-enter-back` snaps that settled page back to `translateX(-22%)` + 0.6 opacity and slides it in again over 380ms. Fast flick → the two motions read as one overshoot with a bounce-back.

**Why keying off `useNavigationType() === 'POP'` is safe here** — and would NOT be in a typical app. The obvious objection is that suppressing every `POP` also kills the in-app back arrow and Android hardware back. It doesn't, because NAV-BACK-1 already forbids those from popping: both `useAppBack` and `useAndroidBackButton` compute `resolveParent(...)` and call `navigate(parent, { replace: true })`, which React Router reports as `REPLACE`. Tab taps and `<Link>`s are `PUSH`; in-route redirects are `REPLACE`. By elimination, the ONLY thing in this app that produces a `POP` is the platform's own back/forward affordance — exactly the case that already animated itself.

That made the "mark our own programmatic pops with a module-level flag and skip only unmarked ones" design unnecessary: there are no programmatic pops to mark. The `replace`-everywhere rule from NAV-BACK-1 is doing that job structurally, which is stronger than a flag (no timing window, nothing to forget to set). The cost is that NAV-BACK-1 becomes load-bearing for the animation layer — recorded in both invariants.

The one in-app `navigate(-1)`, the root-level fallback in `useAndroidBackButton` when `resolveParent('/') === null`, is intentionally left inside the rule. At the root the app has explicitly given up on hierarchy and deferred to raw history; whatever entry that lands on has no forward/back relationship the slide could express, and under `replace`-everywhere it usually lands on the same path anyway (already `null`).

Forward pops (right-edge swipe, browser forward button) are suppressed by the same rule, for the same reason.

**Accepted trade-off:** on a platform whose back gesture does NOT animate the WebView, a gesture-back is now an instant cut instead of a slide. That case is narrow — Android in the Capacitor shell routes back through `useAndroidBackButton` (a `REPLACE`, still animated), so it only affects plain-browser/PWA contexts without an interactive back transition. An instant cut is the correct failure direction: it is a normal-looking swap, where the status quo is a visible overshoot-and-bounce on the platform that ships the app.

**Not verified on device.** The symptom only exists on a real touch device (iOS PWA / Android WebView) with the OS gesture; unit tests can prove `POP → null` and that `REPLACE`/`PUSH` still animate, and nothing more. Re-check on device: (a) the bounce is gone on a fast edge-swipe; (b) the instant swap at gesture-commit does not flash — WebKit tears down the snapshot at commit, and if React's swap lands a frame late the seam would show there.

### NAV-ANIM-10 — the back arrow's flag was consumed in render

Reported 2026-09-30 from beta: *"occasional small flicker coming from a chat BACK to the chatlist. Definitely pre-existing."*

**Evidence.** `nav-back-no-flicker.spec.ts` records every `requestAnimationFrame` from the back-arrow click until the transition settles, sampling each route slot (rows, fallback spinner, transform, opacity). Before the fix, on the dev server, every sample was a single slot: the chat at `translateX(0)` right up to the frame where the list replaced it — one slot, `tx 0`, no `enter-back` / `exit-back` pair at all. An instant cut, where every other navigation in the app slides.

**Root cause.** Since NAV-STACK-1 the in-app back arrow is a real `history.go(-1)`, so it arrives as a `POP`, and NAV-ANIM-9 mutes every `POP` that the app did not flag as its own. The flag was read-AND-cleared by `useNavDirection` **during render**. React Router 7's `BrowserRouter` wraps each location update in `startTransition`; a transition render is interruptible and is restarted from scratch whenever an urgent update lands mid-render — and a chat screen is full of those (message and chat snapshots, typing indicator, scroll and keyboard handlers). The first pass consumed the flag and computed `back`; the restarted pass found the flag gone, computed `null`, and that pass is the one React committed: an un-animated single-slot swap. Occasional in production (it needs an update to land inside the render window), deterministic in dev, where StrictMode replays every render. Nothing to do with the list's data, the lazy-route fallback, or the slot timer — the probe showed none of them.

**Fix.** Mark the MOVE (`from`, `to`), peek it in render, clear it after commit. Alternatives weighed: (a) disable transitions on the router (`useTransitions={false}`) — hides this instance but leaves a render-time side effect waiting for the next replay (StrictMode would still eat it), and gives up concurrent navigation app-wide; (b) carry the marker in history state — `history.go(-1)` cannot attach state to the entry it lands on; (c) move classification into an effect — the slide class must be present on the entering slot's FIRST render (the existing read-in-render comment explains why), so the answer has to be computable in render. Peek-in-render + clear-in-commit keeps (c)'s constraint and removes the side effect. Keying the mark on the exact `(from, to)` pair also means a stale mark can never animate an unrelated platform `POP`.

**What the bug had been hiding in the E2E suite.** Because the dev server (StrictMode) never animated an in-app back since NAV-STACK landed on 2026-09-20, no spec had ever seen two pages co-mounted after a back arrow. `nav-back-hierarchy.spec.ts` located `nav-back` straight after one: with the slide restored, both pages' arrows are in the DOM for `PAGE_ANIM_MS`, so it now waits for the single steady-state slot first. Separately, `nav-pop-no-double-animate.spec.ts` (NAV-ANIM-9) had been failing on the base branch: it set up history with `page.goto('/cards')`, a cold deep link, under which NAV-STACK-4 plants the `/` floor, so the pop landed on `/` instead of `/settings`. It now reaches `/cards` by a tab tap (the real path), and both of its tab locators take the `:visible` link, since the first `a[href]` match is the NavRail's, which is hidden on a phone viewport.

**Trigger to revisit.** Any new render-time read of module state in the navigation layer. The rule is general: render may be replayed, so render reads, commit writes.

### NAV-OVERLAY-1 — the image viewer gets a history entry of its own

**The report.** *"Going back from the image viewer should go back to the chat, not back to the chat list."* Nothing in the hierarchy was wrong: `resolveParent('/chat/:id') === '/'` is right, and it is what `NAV-BACK-CIRCULAR-1` depends on. The viewer simply had no entry, so the platform back — which never asks the app (`NAV-STACK-2`) — popped the chat from under it.

**Alternatives weighed.**
- *A viewer route* (`/chat/:id/media/:key`). Makes the viewer a first-class hierarchy node, but it is mounted from six places (chat bubble, chat-info gallery, chat-header avatar, group-info avatar, one-to-one info avatar, editable avatar), on three different routes, and each would need a sibling route, a `resolveParent` rule and a `NAV_SECTIONS` decision. It would also route-animate the viewer open/close, which is not the product.
- *Intercept back*. Impossible for the iOS edge swipe and browser back — there is no `popstate` veto (`NAV-STACK-2`).
- *A same-URL overlay entry* — chosen. One mechanism in the viewer itself covers every mount, the page underneath is never touched, and it is removable: when the viewer closes by any other path the entry is popped, so the stack returns to the `NAV-STACK-1` chain.

**Costs, stated plainly.** (1) `NAV-STACK-1` is no longer literally "no other shape": the amendment above names the single exception. (2) Browser FORWARD after backing out of the viewer lands on the now-orphaned overlay entry: same URL, viewer closed, harmless, one extra back. (3) If something outside the viewer pushes a route while it is open (a push-notification tap), the overlay entry is left beneath that page: one back later lands on the same chat with the viewer closed. The viewer's own "Go to message" is covered by `replace`; the push-tap case is rare enough not to warrant a global hook.

**Trigger to revisit.** A second overlay that wants the same treatment (the tutor sheet, the review modal): lift `viewerHistory.ts` into a general overlay-entry helper rather than copying it.

### NAV-OVERLAY-2 — Android back closes sheets through an in-memory stack, not history entries (2026-10-01)

**The report.** *"The Android back button doesn't close bottom sheets."* `useAndroidBackButton` knew one overlay, the image viewer (via its history entry), and otherwise climbed the hierarchy, so a ConfirmDialog open on the chat info screen backed out to the chat with the dialog still in flight.

**Alternatives weighed.**
- *Generalise NAV-OVERLAY-1's same-URL history entry* (the trigger that decision named). It would also fix browser/PWA back and the iOS swipe, which no in-app mechanism can intercept. Rejected for now: many sheets navigate from INSIDE themselves (a sheet button that routes, ConfirmDialog confirming a delete that `navigate`s), and each of those would have to `replace` its overlay entry or leave a dead same-URL entry under the pushed route — an extra back that breaks `NAV-STACK-1` for every one of ~25 consumers, where the viewer had exactly one such exit to audit. Sheets also open from inside sheets (CardEditorSheet → LanguagePicker), which multiplies the entries and the ways they can be orphaned.
- *A global `popstate`/keydown handler that finds the topmost `[role=dialog]` in the DOM.* No way to call the overlay's own close (vaul and the hand-rolled modals keep that in React state), and it would bypass guarded closes.
- *An in-memory stack of close callbacks* — chosen. The Android back button IS interceptable (`NAV-STACK-2` names only the iOS swipe and browser back as not), so the stack fully covers the report without touching history: nothing to orphan, nothing to `replace`, and a sheet that navigates simply unmounts and unregisters.

**Costs, stated plainly.** (1) **Browser / PWA back on Android Chrome and the iOS edge swipe still leave the page with a sheet open** — unchanged from before. (2) Order is registration order. Two overlays opening in the SAME commit register child-before-parent (React runs child effects first), so the parent would be "top"; nothing in the app does that today (every nested sheet opens from a tap inside an already-open one). (3) An overlay that forgets to call `useOverlayBack` silently falls back to the old behaviour — `BottomSheet` carries the hook so every sheet built on it is covered by construction; the hand-rolled `role="dialog"` modals are listed in the invariant.

**Trigger to revisit.** A report that browser/PWA back or the iOS swipe should close a sheet — then lift `viewerHistory.ts` into a general overlay-entry helper with a `replace`-on-navigate rule, and keep this stack for Android (it is still what decides which overlay the native press closes).

### NAV-CHROME-2 / NAV-ANIM-12 — the tab bar and the pushed page each showed up in the wrong place (2026-09-30)

**Evidence.** `nav-tabbar-transitions.spec.ts` samples every animation frame of each navigation: each slot's `getBoundingClientRect().left` next to its transform's `translateX`, and each tab bar's position and owning slot. Before the fix: list → chat had NO tab bar in any transition frame while the list slot was still on screen; chat → list painted the bar at `left 0` on the first frame while the list was at `-86px`; contacts → add contact showed both slots offset by a full page from their own transforms (an ancestor scroll).

**Tab bar: why in the slot, and why only sometimes.** Alternatives weighed: (a) keep the bar in `AppShell` and delay `hideTabBar` until the slide settles — it would still pop out at the end rather than travel, and on back would still sit at rest over a receded list; (b) always render the bar inside each slot — correct for one-sided moves, but a tab → tab switch would then slide two bars past each other, which no tab-bar app does; (c) **in the slot when only one side has it, shared and stationary when both do** — chosen: each case gets the behaviour the eye expects, and the rule is a pure function of the two slots' paths.

**Why `/contacts/add` and `/contacts/edit/*` now hide the bar.** The brief was "either hide it consistently or make it work — never visible-but-dead". `/contacts/new-group` already hid it as a focused form; add and edit are the same shape (a single form whose goal is its submit button, keyboard up on mount), so hiding is the consistent rule rather than a special case. The dead bar itself was NOT reproduced in chromium or webkit-mobile (the E2E never asserted a tap on the old add-contact bar); what the red run DID show is `#root` scrolled 390px sideways by the form's autofocus mid-transition. The likeliest on-device mechanism is that same focus-driven scroll plus iOS's own layout-viewport shift on focus, which desyncs hit-testing from paint for bottom chrome — unverified. Hiding the bar on the form makes the question moot there; NAV-CHROME-4's tap assertion covers the bar where it remains. **Revisit if** the owner wants the bar on those forms; the E2E then flips to NAV-CHROME-4's tap assertion on `/contacts/add`.

**Trigger to revisit NAV-ANIM-12.** Anything that makes the slot area a scroll container again (`overflow: auto/hidden` without the reset), or a transition that moves slots by anything other than a transform.

### Harness note (2026-09-30): the back-arrow tap that never arrives on webkit-mobile

`nav-back-hierarchy.spec.ts` failed about once in 15 runs on webkit-mobile, on the base commit (6a1e2576: 1 failure in 90 tests over 15 repeats; the coordinator's run: 1 in 14) and on the NAV-CHROME head alike: the back arrow on a cold-loaded `/chat/:id/info` was clicked, and 15 s later the URL was still `/info`.

**Evidence.** An instrumented copy of the spec logged, from `addInitScript` (so from the first line of the document): every `pushState`/`replaceState`/`history.go`, every `popstate`, and every `click` seen by a capture-phase listener on `window`. The failing run recorded the boot seeding (`replaceState /`, `pushState /chat/:id`, `pushState /chat/:id/info`), the router's stamp, and then **nothing** — no click event anywhere in the document, so no `useAppBack`, no `go(-1)`. Playwright nevertheless reported the click as performed. 20 fresh-context and 80 same-context probe iterations with the same instrumentation never lost a tap, so the loss needs the full spec's load (new context + sign-in + emulator writes landing during the first paint).

**What it is not.** Not the pop (`go(-1)` was never called), not `canPopToParent` (never reached), not the NAV-ANIM-12 clip or the NAV-CHROME slot wrappers (present on base). Unverified hypothesis: WebKit's touch-emulation path suppressing the synthesized click when the page's content changes during the tap window (iOS's content-change observer does this on device, which a real user experiences as "tap did nothing, tap again").

**Fix, in the harness.** `tests/e2e/helpers/navBack.ts` `tapNavBack(page)` counts the arrow taps the page actually receives and re-taps only while that count is ZERO, so a delivered tap is never repeated (a slow pop cannot become a double back, and a real regression — tap delivered, nothing happens — still fails the caller's URL assertion). Each re-tap is annotated `nav-back-retap` on the test and logged `NAVBACK-RETAP`, so the frequency stays visible. **Revisit if** a re-tap ever shows up outside webkit-mobile, or on a warm page — that would be an app bug, not this.


**Follow-up (2026-10-14): the arrow of a page that is no longer the URL's.** In the 0.3.1 release run `learning-tips.spec.ts` (`TIPS-TRY-2`) failed once on chromium: back from `/cards/practice/hub?from=tips` landed on `/`, not `/tips`. React Router renders a navigation inside `startTransition`, so while the next screen's lazy chunk loads (normally prefetched on idle, BOOT-SPLIT-2; not yet under load) the URL has already moved but the OLD page is still the one slot on screen, and its arrow is the only `nav-back` in the DOM. An instrumented run showed it: URL `…/hub?from=tips`, one slot `/tips`, one arrow resolving to `/`. Tapping it is a correct back from the page shown, so this is a harness defect, not an app one: the test treated "URL changed" as "new page on screen". It reproduced 8/8 at 6x CPU throttle. `tapNavBack` now waits until the single settled slot is the page the URL names and holds its own arrow: 48/48 under the same throttle. The same wait removed the chromium `NAVBACK-RETAP 3 taps` that `TIPS-TRY-1` logged on 9 of 10 runs, so that re-tap was this defect, not the app bug the revisit note above guards against.

The separate `page.goto: WebKit encountered an internal error` is a WebKit browser crash under the 4-CPU box's load, already documented (and given one retry) in `tests/e2e/playwright.emulator.config.ts`. It did not recur in 15 + 15 webkit repeats of this spec on base and head.
